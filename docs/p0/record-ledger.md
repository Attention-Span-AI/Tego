# pkg/spec/record + internal/ledger (P0 detailed spec)

## 1. Purpose and boundaries

**`pkg/spec/record`** — the wire format of one run's audit trail. Owns: `Kind`, `Verdict`, `Source`, `Authority`, `Reason`, `Attribution`, `RunRef`, `Event`, and the canonical JSON-lines codec (`MarshalLine`/`Decode`). It defines the *shape* of a line and the rule that produces `id`/`prev`. It does no file I/O, knows nothing of run directories, locks, blobs, gc, or the disk at all. Pure data + one deterministic encode/decode pair.

**`internal/ledger`** — the only code in the product that writes `events.jsonl`. Owns the run directory, the `flock`, the blob store, the `chain.log` anchor, the torn-line-tolerant `Reader`, and `gc`. It also **provides** the redaction and blob-split logic as composable pipeline `Stage`s (`docs/REPO-LAYOUT.md`'s middleware table: "redaction, blob split ... `internal/ledger` (redaction, blobs)"), but does not invoke them itself — they are wired, by `internal/runtime`, in front of the ledger's own `Sink` (`Compose(stampRule, attributeStep, redact, splitBlobs)(ledger.Write)`, same doc, and `docs/P0-DESIGN.md` §2.10: "Redaction stage before `Append`"). Per `docs/REPO-LAYOUT.md` this package is the Repository/data-access layer: "the ledger writer and reader; the only store." It never decides whether an action is allowed and never derives decisions or steps (`derive` does that upstream). It persists what the pipeline hands it and reads it back byte-for-byte.

**Imports allowed** (`doc.go`, `docs/REPO-LAYOUT.md` §Import direction):
- `pkg/spec/record` → standard library only. Must not import anything under `internal/`, must not import `yaml.v3` (only `pkg/spec/agent` and `pkg/spec/config` get that exception).
- `internal/ledger` → `pkg/spec/record`, standard library only. Must not import `internal/runtime`, `internal/check`, or any `capture/derive/enforce` package (`docs/ARCHITECTURE.md` §1). This holds even though `internal/ledger` *exports* the `redact`/`splitBlobs` `Stage` functions `internal/runtime` composes: the dependency arrow still points one way (`runtime` imports `ledger`, never the reverse).

**Must not**: `pkg/spec/record` must not perform policy logic (no verdict computation — it only carries the `Verdict` a caller already decided). `internal/ledger` must not perform network I/O, must not re-derive or mutate an event's action fields (only `seq`, `prev`, `id` are ledger-assigned), and must never rewrite a byte once written — "ledgers are never rewritten: rewriting would change every `id` and break the anchor" (`spec/record/v1/README.md`).

## 2. Models

### 2.1 `pkg/spec/record` (package `record`)

```go
package record

// Kind is the v1 closed set (spec/record/v1/README.md). P0 writers emit a subset; Decode must accept all of
// them because the schema is frozen for the whole product, not per phase (docs/VERSIONING.md §2).
type Kind string
const (
    KindRunStart    Kind = "run_start"
    KindRunEnd      Kind = "run_end"
    KindExec        Kind = "exec"
    KindFS          Kind = "fs"
    KindNet         Kind = "net"
    KindMCP         Kind = "mcp"
    KindSSLRequest  Kind = "ssl_request"
    KindSSLResponse Kind = "ssl_response"
    KindDecision    Kind = "decision"
    KindAsk         Kind = "ask"       // P1 (E13); schema-only in P0, no writer emits it
    KindAnswer      Kind = "answer"    // P1
    KindRefused     Kind = "refused"
    KindGap         Kind = "gap"
    KindBoundary    Kind = "boundary"  // P1 general (E46); Docker-specifics P2/P1-conditional (E43); schema-only in P0
    KindLimit       Kind = "limit"
)

type Verdict string // allow ask refused observed
type Authority string // rule gate human llm
type Source string  // kernel landlock seccomp fanotify ssl forwarder hook python node supervisor proxy

// Reason is spec/reason/REASON-CHANNEL.md's 16-code closed set, plus three codes this document adds because they
// are independently normative elsewhere but absent from that closed-set list — a real gap in the owning spec, not
// a license to invent codes freely. See §11 for the note this must carry to REASON-CHANNEL.md's owner.
type Reason string
const (
    ReasonWriteOutsideContract  Reason = "write-outside-contract"
    ReasonDeleteOutsideContract Reason = "delete-outside-contract"
    ReasonRenameOutsideContract Reason = "rename-outside-contract"
    ReasonReadDenied            Reason = "read-denied"
    ReasonExecNotAllowed        Reason = "exec-not-allowed"
    ReasonExecGate              Reason = "exec-gate"
    ReasonNetNotAllowed         Reason = "net-not-allowed"
    ReasonNetGate                Reason = "net-gate"
    ReasonAskDenied              Reason = "ask-denied"
    ReasonAskTimeout             Reason = "ask-timeout"
    ReasonLimitTokens            Reason = "limit-tokens"
    ReasonLimitCost              Reason = "limit-cost"
    ReasonLimitWall              Reason = "limit-wall"
    ReasonLimitStall             Reason = "limit-stall"
    ReasonOOM                    Reason = "oom"
    ReasonPids                   Reason = "pids"
    ReasonPathUnresolved         Reason = "path-unresolved"   // SEMANTICS §2: disconnected dentry / walk exhausted
    ReasonAskUnreadable          Reason = "ask-unreadable"     // ARCHITECTURE §7: Yama, non-dumpable target
    ReasonAskUnavailable         Reason = "ask-unavailable"    // SEMANTICS §6, echoed ARCHITECTURE §9: adopted cgroups
)

// Attribution is present only on exec, fs, net, mcp events (spec/record/v1/README.md); zero value elsewhere.
type Attribution struct {
    Thread     string `json:"thread,omitempty"`
    Step       int    `json:"step,omitempty"`
    ToolUseID  string `json:"tool_use_id,omitempty"` // the reply's tool_use, exactly under method tool_id (record_minor 29)
    Confidence string `json:"confidence,omitempty"` // exact | likely | unattributed
    Method     string `json:"method,omitempty"`     // tool_id | tid | time | none
}

// RunRef identifies the run a Writer/Reader is bound to; supplied once at Open, stamped on every event so
// per-event callers never repeat it (avoids drift between events.jsonl and the run directory name).
type RunRef struct {
    ID    string // run id, r-<host8>-<time36>-<rand6> (spec/identity/RUN-IDENTITY.md)
    Agent string // contract name, [a-z0-9-]{1,40}
}

// Event is the in-memory representation of one line. Field order below IS the canonical wire order (§5 R1).
type Event struct {
    V      int       `json:"v"`               // 1, frozen at M0
    Seq    uint64     `json:"seq"`             // 0-based, Writer-assigned, monotonic within a run
    ID     string     `json:"id"`              // sha256 of the canonical line, hex (§5 R2)
    Prev   string     `json:"prev"`            // id of the previous line; "" for run_start
    TS     time.Time  `json:"ts"`              // wall clock, RFC 3339Nano UTC; may be non-monotonic (§5 R7)
    MonoNS uint64     `json:"mono_ns"`         // CLOCK_MONOTONIC reading at capture, ns; monotonic within one boot only
    Run    string     `json:"run"`             // run id, Writer-stamped from RunRef
    Agent  string     `json:"agent"`           // agent id, Writer-stamped from RunRef
    PID    int        `json:"pid"`
    TID    int        `json:"tid"`
    Cgroup uint64     `json:"cgroup"`
    Kind   Kind       `json:"kind"`
    Source Source     `json:"source"`
    Rule   string     `json:"rule,omitempty"`      // action events only: declared entry name or "unmatched"
    Verdict Verdict   `json:"verdict,omitempty"`   // action events only
    Authority Authority `json:"authority,omitempty"`
    Reason Reason      `json:"reason,omitempty"`    // refused events (and gate-escalated actions)
    Attr   Attribution `json:"attribution,omitempty"` // exec fs net mcp only; omitted entirely when zero value
    Payload json.RawMessage `json:"-"`            // kind-specific object; spliced into the top level, never nested (§5 R3)
}

func (e *Event) MarshalLine() ([]byte, error) // §5 R1-R4
func Decode(line []byte) (*Event, error)      // tolerant of unknown top-level keys; validates v==1; §5 R5
```

Validation rules on `Event` (enforced by `MarshalLine`, not by a separate `Validate`): `V` must be `1`; `Kind` must be one of the 15 constants above; `Seq`/`ID`/`Prev`/`Run`/`Agent` must be non-empty except `Prev` on the first event of a run; `Rule`/`Verdict`/`Authority` are required (non-empty) when `Kind` ∈ {exec, fs, net, mcp}, forbidden (must be zero value, `omitempty` drops them) otherwise; `Attr` is required for the same four kinds once `docs/FEATURES.md` E55 attribution is wired (P0 ships `{confidence:"unattributed", method:"none"}` or `{method:"time"}` — never omitted for those four kinds, always omitted for the other eleven).

**The additive `run_start`/`run_end` fields** (optional within v1, `docs/VERSIONING.md` §2; a reader of an older ledger finds them absent and must say so rather than assume a value):

- `run_start.limits` carries a key exactly when the run had a budget on that dimension, and the key's value is the budget `limits.Watcher` enforces. An explicit `0` is the tightest budget, not the absence of one (`limits-check-doctor-cli.md` E16), so `tokens`, `cost_usd` and `repeats` are pointers in Go: a plain number under `omitempty` dropped the `0` and left a reader seeing no budget on a run the watcher would end at its first token. An absent key is the only spelling of "unbounded"; a block with no key is not written at all.
- `run_start.capabilities` is the **capability line**: one key per row of `spec/backend/CAPABILITIES.md`, spelled as `pkg/spec/backend.Capability` names it (`fs.deny_write`, `fs.deny_read`, `record.reads_mmap_chmod`, `capture.model_traffic`, ...), `true` when this run could do it. Every row is written, `false` included — a `false` is the statement that the run lacked it, and a key a reader does not know is a row a newer binary added, kept rather than dropped. It is filled once, at `run_start`, from the enforcement handle's own set when the handle reports one (`enforce.Reporter`: the tier's row narrowed by an unenforced `deny_read`, the Landlock ABI, a tier-2 run with no fanotify listener, `net.unix_abstract_scope` set from the Landlock ruleset the run applies — at tier 2 the inherited one, read by the tier-2 handle — which holds the scope at ABI ≥ 6 (`agent-contract.md` R19, added 2026-09-23), and a contract's `exec: {anonymous: true}`, which clears `exec.deny` in the tier-1 handle because with no memfd arm `exec.allow` no longer bounds what runs — `enforce-landlock.md` R11a, added 2026-09-23, and at tier 2 read by the tier-2 handle from the inherited row as `net.unix_abstract_scope` is; the tier-2 handle does not clear `net.unix` for a unix entry, which `connect_unix`/`sendmsg_unix` decide on 6.7+ and tier 1 decides on every kernel, `enforce-cgroup-observe.md` §5 R7) and from the backend's row otherwise. The rows only the run can answer are then set from the run, not left at the tier's value: `capture.model_traffic` is `true` exactly when `run_start.capture` is not `off`, both read once from the capture sources whose mechanism runs (a source that started but reports its own `mechanism-unavailable` gap, as an uprobe source whose capture object would not load does, counts as not running, and so does a source that follows the kernel record while no kernel recorder reads for the run, since nothing hands it an exec or an open); an observe run, whose row is empty because it enforces nothing, takes tier 1's `record.exec_open_connect`, `record.reads_mmap_chmod` and `log.allowed_with_rule`, because it records through tier 1's filter and supervisor (`supervisor.md` R30); `record: off` makes those three rows `false` on every tier, because the run then keeps refusals only; `record.reads_mmap_chmod` is `false` when the run's reads cannot reach its record (tier 1 or an observe run without `record: full`, whose filter does not notify read-opens; a tier that records reads from a kernel ring when no kernel recorder drains it for this run — none was built, or the one built reports its own `kernel-record-unavailable` gap because another run of the build holds the ring or the run had no row to scope by — and the tier-1 filter it inherits does not notify read-opens either, which is every record mode but `full`); and `ask` is `true` only when the run has compiled approval configuration, an available authenticated broker and a started supervisor notification loop in an enforcing, non-records-only run (`internal/runtime/runstart.go` `capabilityLine`, `TestAskCapabilityRequiresStartedAvailableBroker`). This readiness row does not promise unsupported exec or UDP approval completion (unix connect approval is completed since 2026-10-19, supervisor R11c), or override independent policy floors (`agent-contract.md` R22/R22a). `gate.net_completion` (ADR 0041 D7's gate relay) is `true` only while a started supervisor answers the run's notifications, as for `ask`, and `fs.protected_write_targets` is `true` exactly where a decision plane mode decides the run (`decision_plane` `lsm` or `fmod_ret`), the reading under which `run_start.best_effort` drops `deny_write/default`, so the two never disagree (*added 2026-10-16*, `TestCapabilityLineCompletionRows`); `fs.deny_read.created_later` (ADR 0043) is `true` exactly where the plane's name check decides the run's slot, a plane mode with the table's name rows (`enforce/cgroup` `Handle.Capabilities`), and `false` on the fanotify fallback and for a table with no name entry (*added 2026-10-20*, `TestCapabilitiesNameEntriesWhereThePlaneChecksNames`). `containers.adopted` and `containers.namespace_sandbox` remain `false` because `docker` and `containers` are refused as not yet supported (`agent-contract.md` R2). `net.http_rules` is true only when this run has a compiled HTTP policy and its required forwarder listeners actually started. TCP, UDP and Unix kernel destination rows are narrowed by the handle’s measured attachments, not inferred from the tier name. The static matrix keeps conditional rows, since it describes the tier. `status` renders it (`limits-check-doctor-cli.md` R-cap). The static matrix answers what a tier can do; this answers what one run did have.
- At record minor 4, `run_start.net_assurance` reports `best-effort` or `kernel`; `net_guarantees` reports measured `tcp`, `udp`, `unix`, `socket_imports_denied` and `listeners_denied` booleans (and, additive within v1, 2026-10-16, `socket_families`: ADR 0018's bound held on every path the run can make a socket by, or turn one into another family by, `TCP_ULP` included from 2026-10-17). Strict assurance refuses missing coverage before agent release and denies socket import/listener syscalls; these fields do not promise ingress filtering or revocation of existing connections. HTTP decisions use `net` with `proto: http`, `op: http_request`, `http_authority`, `method` and query-free, redacted `path`. The common `authority` remains the decision source.
- At record minor 14 (2026-10-24, agent-contract.md R27, ADR 0062), `run_start.harness` names the harness the launcher
  provisioned for and whether it did (`why`: `no-provisioner`, `reason-unavailable`, `hook-refused`,
  `hook-not-granted`), with the files it made, the reason file and the `hook-state` directory; absent for `harness:
  none` and an adopted run. `runtime_grants` may name `fs.harness-state[<path>]`.
- At record minor 20 (2026-10-25, ADR 0064), `run_start.harness.hook` is `{argv, granted}` for every provision that
  names a hook, `granted` when the launcher granted its exact argv under an allow-list contract; `runtime_grants` then
  names `exec.harness-hook[<tego binary>]`, the rule of the hook's exec and of the refusal of every other vector of the
  binary. `why` may also be `harness-hook-writable` (the binary or its loader under a write entry or an `fs.ask` scope by
  a name the launcher sees, or with names it cannot see: more than one link, or an unreadable mount table).
- At record minor 13 (2026-10-20, agent-contract.md R26), `run_start.contract_source` names the contract file the launching user named: `path`, its absolute path (the file read: a `..` after a link is taken from the link's target, ADR 0059), and, when the file was resolved from an agent name (`tego run retriever`), `name` and `registry` (`project`, the working directory's agent.yaml or .tego/agents/<name>.yaml; `user`, the machine config's `registry:`). It is the file whose bytes the run compiled, so `contract_hash` says what the contract was and this where it came from. Absent at revision 13 or later, tego generated the contract (`watch` or `adopt` with no `--boundary`); absent in a ledger that predates it.
- At record minor 15 (2026-10-24, ADR 0066 D6), `run_start.profiles` lists every profile the run's contract merged through `extends`, in merge order, each once: `name` (the extends name), `source` (`builtin` for a profile built into tego, under `tego/`; `dir` for a file of the profiles directory) and `sha256` (hex, of the bytes read). `contract_hash` covers the merged contract; this says which profiles gave it. Absent at revision 15 or later, the contract extends no profile; absent in a ledger that predates it.
- At record minor 17 (2026-10-25, ADR 0073), `run_start` carries the run's identity, each what the launcher read when the run started and none a verified fact about a person: `launcher_uid` (the launcher's real uid, on every run_start, 0 included), `launcher_user` (its passwd name), `sudo_uid` and `sudo_user` (only when the launcher's real and effective uid were 0 in the initial user namespace and its own process's `SUDO_UID`, the one its drop to the invoking account reads and never the agent's environment, was the plain decimal of a uid; the name from passwd, never `SUDO_USER`; sudo's claim, which any root process can set), `host` (the kernel nodename, at most 255 bytes with no control, format, line or paragraph separator character, else absent), `parent_run` (the run it was started in, a valid run id: the enclosing run's `TEGO_RUN_ID` for a `tego run` inside a governed agent, else `TEGO_PARENT_RUN`; the environment's claim, not a link tego checked, until nested runs are verified), `labels` (the caller's, `identity.ValidLabels`), `role` (reserved: `check` marks a run a checking command started, and no shipped command sets it; absent for the agent's own run) and `contract_revision` (the contract's `revision`, agent-contract.md R28). `host` and `role` are run_start payload keys, never common fields. At minor 17 or later an absent optional one means the run had none; absent in a ledger that predates it. The compact per-line stamps a reader joins on are not these.
- At record minor 11 (2026-10-16, agent-contract.md R10a), `run_start.runtime_grants` lists the rule name of every entry the run added to its table on its own authority (`net.capture[<addr>]`, `net.dns-broker[unix:<path>]`, `fs.codex_home[<path>]`); the contract hash does not cover them. `net.resolver` (supervisor.md R14) is a decision, not an entry, and is not listed; its lines name it. Absent at revision 11 or later, the run added no such entry.
- At record minor 6 (2026-10-05, ADR 0041 D7), `run_start.best_effort` lists the stable ids of the run's disclosed best-effort cells (`agent.RuleTable.BestEffortCellsAt`): gate rules whose supervisor decision is taken on copied syscall facts and continued when it does not refuse, never counted as enforced, and (ADR 0041 D1 (a)) `deny_write/default` where no kernel decision plane decides the run's built-in `deny_write` targets. It is static for the compiled contract, absent when there is none, and not a `gap` (that kind is for events that happened). `status` prints it.
- `run_end` with `reason: orphaned` records `exit_code: 125`, the identity contract's logical launcher failure. A sweep or reaper cannot recover the agent's wait status; this code is neither that status nor the sweeping process's exit. Older sweepers omitted the field and decoded it as zero. `status` interprets an orphaned zero as 125 while leaving the original ledger bytes and hashes intact; it retains explicit nonzero codes and an ordinary `reason: exit` with zero.
- `run_end.supervisor.orphaned` and `.starved` are the supervisor's E35 and R21 counters (`supervisor.md`): syscalls it performed that the agent abandoned before the answer arrived, and the times its worker pool could not backfill a parked relay. Both counts used to stop in the loop. Under `record: summary` or `full` each orphaned call also has its own `net` line with `result_unknown`; under `record: off` no allowed `net` line is written, so `orphaned` is the only trace of them. A starved backfill is otherwise only a line in tego's own log (`~/.tego/tego.log` for a CLI run), which is not part of the run's record. No view reads either count yet; they are in the record so one can.
- `run_end.resources` is what the run's cgroup said the run used, read once at shutdown before the cgroup was removed,
  normally after the tree emptied (a tree still populated then is read as it stands and can keep adding to the
  files afterwards, so its values are a lower bound: one whose wait for the cgroup to empty failed while the run's
  context was still live (the tree is killed then, and `run_end.detail` says so), or one that outlived the kill; `runtime-launch.md` §4.1 steps 12-13,
  `cgroup.ReadResources`): `memory_peak` is `memory.peak` in bytes, `pids_peak` is `pids.peak`, the `cpu_*` keys
  are `cpu.stat`'s `usage_usec`, `user_usec`, `system_usec`, `nr_throttled` and `throttled_usec`, and `memory_events`
  is `memory.events`' `high`, `max`, `oom` and `oom_kill`, all cumulative over the run's whole cgroup subtree. A key
  is present only when its file and key existed and the file could be read: `memory_peak` needs Linux 5.19 and the
  memory controller, `pids_peak` a kernel with `pids.peak` and the pids controller, the throttling keys the cpu
  controller, `memory_events` the memory controller; the `cpu.stat` usage keys exist on every cgroup v2 kernel. An
  absent key is unknown, never zero, and a `0` that is present is the kernel's zero. The whole object is absent when
  nothing could be read (a run that failed before its cgroup existed, or an older binary), and a file that could not
  be read, or a value that is not a count, leaves its keys absent too, with a line in tego's own log. It is what an
  operator sizes `limits.memory` and `limits.pids` from. `measure` and `status <run>` render it, an absent key as
  `unknown` and never `0` (`limits-check-doctor-cli.md` R-res; added 2026-09-23, rendered the same day).

`ask`/`answer`/`boundary` payload types are declared (`AskPayload{id,hold}`, `AnswerPayload{ask_id,by,after_s}`, `BoundaryPayload{context_bytes,dockerfile_sha256,tags,network_mode}`) per `spec/record/v1/README.md` so `Decode` never fails on a future write from a P1/P2 binary reading an older event; no P0 code constructs them.

**Hand-over rule** (`docs/OPERATIONS.md`: "the files a root run creates for it are handed to that user"). A root launcher writes, by default, into the invoking user's `~/.tego`. What it creates inside a directory another uid owns — `~/.tego` and `~/.tego/runs` (`MakeDirs`, used for the ledger root and the anchor's directory), `chain.log`, and the run directory with every file in it (`handOverDir`, called by `Close` on the directory descriptor the Writer held for the run) — is handed to that directory's owner and group. Before this rule all of it stayed root's 0700/0600, so the user's own `status`, `events` and `drift` could not read the run and their next unprivileged run could create neither its directory nor its anchor line. Only what a call itself created is handed over — a directory its `mkdirat` made, a file its `O_CREAT|O_EXCL` open made, a run directory root made and wrote alone — never an entry that was already there under the name: the directory's owner can rename a file of root's into their own directory, and renaming never let them read it, so handing over whatever root-owned file sat under a name would give them its contents. So `chain.log` is created `O_EXCL` and handed over only when that open made it, `handOverDir` walks only a run directory this process owns, and a Writer working in a run directory another uid owns (a root sweep ending a user's orphan) hands over each file it creates there as it creates it. A tree root owns (an operator's `/var/lib/tego/runs`) keeps what root made in it. Root reaches every directory it writes into — the ledger root (`MakeDirs`, and `MakeRunDir`, which then makes the run directory through the descriptor the walk ended on), the anchor's directory (`Append`, `Head`, `ProbeAnchor`) — by walking it one component at a time from `/`, and in a directory that is not root's alone (owned by another uid, or group- or other-writable) a component is opened `O_NOFOLLOW`: a symlink there is refused (`ErrLinkRefused`), never followed. A link in a directory only root can change is followed as the kernel follows it — an operator's ledger root moved to a bigger disk. A hard link, a FIFO or another uid's file is left alone. **The live run is written by descriptor.** `Writer.Open` reaches the run directory by the same walk and keeps it open until `Close`; `lock`, `events.jsonl`, `blobs/` and its files, `contract.yaml` and `last-refusal.json` are all named relative to that descriptor (`openat`, `mkdirat`, `renameat`), each file opened `O_NOFOLLOW` and refused unless regular (and single-linked, for root), a new one made `O_CREAT|O_EXCL` or as a temporary file renamed into place; the launcher's lock-holder line is written through the flocked descriptor (`WriteLockInfo`), and `Close` hands over the directory it held, not whatever the path names by then. The launcher opens its run directory `WithFreshRunDir()`, so between `MakeRunDir` and `Open` a directory renamed in under the run's name — one the process does not own, or one that already holds anything — is refused (`os.ErrExist`). **Residual, stated rather than hidden:** what is still reached by path during a live root run is read-only or stays in the user's own tree — the launcher's `lstat` and read of `stop.request` (at most 64 bytes, `O_NOFOLLOW`), so a user who replaced their ledger root could make a stop signal read as `reason=stopped` with a grace of their choosing, the enforcement tier's identity holds on the run directory and `contract.yaml` (deny nodes), the removal of the run directory when the launch fails before `run_start`, and a uprobe source's own blob store, which walks to `blobs/` afresh for every write, as root refusing a link in a directory the user can change, so its blobs land in the run's own `blobs/` or, after such a replacement, in whatever real directory the user's tree then names, never through a link: one the user owns, or a root-owned run directory already in it, because a rename inside a directory the user owns needs no write on the root-owned directory it moves (`mv runs/X runs/X.aside; mv runs/Y runs/X` sends run X's uprobe blobs into run Y's `blobs/`). The bytes are the user's own agent traffic, and they cannot leave the user's tree, since links are refused and moving a root-owned directory to another parent needs write on it. A root launcher that must not depend on the user leaving their tree alone uses a root-owned `ledger_root` (the server setting); an unprivileged run is not exposed, since whatever a link reaches it could already write. The run directory is handed over only after `Close`: while the run is live it stays root's 0700, so the user cannot plant a link under a name root is about to create — the price is that a live root run is readable only as root. A ledger root, or a `chain.log`, that an earlier root run already left root-owned keeps that owner (only what a call creates is handed over), and the user's own next unprivileged run is refused before the agent starts — at the anchor probe for a `chain.log` (`runtime-launch.md` case 37, §7), making its run directory for a ledger root; `chown -R` it once. A root launcher that dies leaves its run root's, and a root sweep that ends it hands it over at that `Close`.

**Live index** (*added 2026-09-24*). `tego run` swept every run directory before it started (`GC` with no retention): a start measured 31 ms on an empty ledger root and 70 ms with 530 runs, about 73 µs per stored run, so some 2 s at 30,000 runs. With the index a start costs the same over 2,000 sealed runs as over none (medians of 30 interleaved starts of `run -- true` on the development machine: 118.8 ms before and 14.6 ms after over 2,000 runs, 50.5 and 16.3 ms over 530, 12.8 and 13.0 ms over none), and one start over 615 runs makes 2,739 system calls where it made 12,801 (`openat` 1,437 → 229, `pread64` 1,858 → 20, `fcntl` 1,353 → 129). `<ledger_root>/.live` now names the runs `run` and `stop` sweep: one empty entry per run whose launcher has taken its lock and not yet finished with it. The launcher keeps an order that makes it complete. It makes the run directory (`MakeRunDir`), takes the lock (`Open`), lists the run (`MarkLive`), and only then writes `run_start`; after `Close` it removes the run's scope and only then clears the entry (`ClearLive`) — on the release goroutine when a source's `Stop` is still running, and not at all when the removal failed (`runtime-launch.md` R8) — and only when the run reads as ended (or its directory is gone, for a run that never started). So a run that can be lost — `run_start` written, no `run_end`, lock free — is listed whatever instant its launcher died at. A launcher killed between the run directory and the entry left a run with no `run_start` and no cgroup yet, which no sweep ends and `gc`'s retention removes; one killed after `run_end` (between the append and the anchor line, the lock release, the scope's removal or the clear) left the entry of an ended run, which the next sweep meets as below; one whose `Close` could not append `run_end` keeps its entry, and the next sweep ends the run as orphaned. A launcher that cannot list its run does not start it (exit 125): the run would be reachable by no sweep but `gc`'s. `SweepLive` (§4) reads each entry's name and nothing else: a name that is no run id is passed over and left, an entry is never opened (a FIFO or a link planted as one blocks and redirects nothing), and the run it names is probed only when it is a directory directly in the ledger root, not a link — what `List` would find there. An entry therefore costs a sweep one `fstatat` and at most one tail read of a run in the root, and cannot aim it anywhere else; anyone who can plant entries can write the ledger root already. The index is opened `O_NOFOLLOW` by every sweeper, and a sweep that cannot read it, or finds none — a root written only by a tego that kept no index, or whose index was deleted — makes `GC`'s full pass with nothing removed instead, so an orphan the index could not name is still ended. A root launcher lists its run under the hand-over rule: the index is reached by the same walk (a link in a directory that is not root's alone is refused, `ErrLinkRefused`, and the run does not start), an index directory root creates in a ledger root another uid owns is handed to that uid as `MakeDirs` hands over what it creates, and so is an entry root creates there, `O_CREAT|O_EXCL|O_NOFOLLOW` so a name already there is neither followed nor handed over. `gc` still walks every run directory and never consults the index, which is what keeps the index a cache (ADR 0004): deleting `.live` costs speed, never an orphan. **An ended run still listed.** `Close` appends `run_end`, fsyncs, then appends the anchor line, and the launcher removes the run's scope before `ClearLive`: a launcher killed between `run_end` and the anchor line leaves an ended run with no anchor, which `events --verify` would read as `ErrAnchorMissing` (`[ledger-corrupt]`) forever, and one killed before its scope's removal leaves an empty scope nothing else removes (reproduced with a `SIGKILL` at each point). `SweepLive` meets such a run while its entry is still there. It takes the run's lock (`LOCK_EX|LOCK_NB`; held, the entry stays for the next sweep: a launcher still inside `Close`, or a process of the run holding a dead launcher's lock); with the lock, a run whose anchor has no line for it is verified with no anchor — every line chained, valid and this run's, `run_start` first and `run_end` last — and anchored at the ledger's own last id in the anchor the Writer options name (the one its launcher would have used: `WithSweepAnchor` in `internal/runtime`, the run owner's), and the repair is logged. A repair that fails on the anchor rather than on the ledger — `Head` cannot read `chain.log`, or `Append` cannot write its line (`ErrAnchorWrite`) — keeps the entry and is reported, so the next sweep tries again; so does a `Verify` cut short by a cancelled context or a read that failed (EIO). Only a verification failure (`ErrUnverified`, `ErrCorruptLedger`) — a chain that does not verify, or is not one whole run of its own — is reported and not anchored, since the anchor would vouch for it, and its entry is cleared; that includes a ledger with no `run_start` (an old launcher's unwind wrote `run_end` as its line 0), which `Verify` refuses. Then the ended hook (`WithEndedHook`) runs with the run's agent: `internal/runtime` leaves a launcher that is alive to clear its own entry (the entry stays), and for one that is gone finds the scope as an orphan's is, removes it — killing anything left in it — and logs it; a tree that stays keeps the entry. What cannot be recovered is the rest of the dead launcher's cleanup: at tier 2 its `Detach` never ran, and its verdict rows, `run_set` rows and, if it was the last launcher of its build, the shared pins stay as `enforce-cgroup-observe.md` §6 E26, E32 and E38 describe for a killed launcher. `gc` has no index and leaves an ended run alone. Because the entry is cleared only after the scope is removed, a launcher killed or exiting between the two leaves the run listed for the ended hook. A run directory whose `lock` file is missing is not repaired: no lock can be held on it, so two sweeps could both find the run unanchored and both append its line, which `Head` then refuses as two heads; the entry goes as it would with the lock free, and `events --verify` reports the run. The repair stands against a launcher killed inside `Close`, not against someone who can write the ledger root: that writer can put a whole chain that verifies under a run id no anchor names and have a sweep anchor it. The anchor lives outside the ledger root so that editing or deleting a run already anchored is seen; a run never anchored has only its own ledger to vouch for it. A run another host minted (its id's `host8` is not this host's, `WithForeignRun`) is left alone entirely: its entry stays until its run directory is gone (which `gc`'s retention brings about for a foreign run, §4), and nothing is swept, repaired or hooked for it, since its lock is a lock on another machine and its anchor that machine's launcher's.

**Modes taken from the owner** (*added 2026-11-02*, GAPS C52). The modes in the table are what tego makes, and nothing stops a run's agent from changing them: it runs as the user who owns them, and no Landlock ABI has a chmod right (CAPABILITIES `fs.deny_chmod`), so with no write entry near them it can still `chmod 000` `~/.tego`, the per-user config layer (`~/.tego/config.yaml`) and `tego.log` in it, `chain.log`, the ledger root, `.live`, tego's runtime parent (`$XDG_RUNTIME_DIR/tego`), and its own run directory, runtime directory and the files in them. Their contents and the record are unchanged, but tego could no longer search, read or write them: the run's `Close` failed its directory's fsync and its anchor (`ErrAnchorWrite`, exit 125), and every later run failed, at the config's load (`[config-untrusted]`), at compile, which could not place the anchor (agent-contract.md R10), or making its runtime directory (`[run]`). So `internal/runtime` restores them where they are needed (`ownstate.go`): `tego run` first gives back `~/.tego`, the config layer and `tego.log` (the home is the one tego keeps its own log under: the invoking user's passwd home, where the layer is read), before it reads the machine config, then `chain.log`, the directory that holds it, the ledger root, `.live` and the runtime parent, before it compiles (`RestoreOwnState`); and every run at its end, just before `Close` and once no process of the run is left, restores those, the config layer and `tego.log` included (`Deps.UserState`), and its run directory with every entry in it, `blobs/` and its blobs included, and its runtime directory, so that shutdown can remove it. A mode is restored only on a directory or a regular file the launcher's euid owns, of the type tego makes at that name, that lacks an owner right tego needs (read, write and search on a directory, read and write on a file it writes, read on the config layer, which it only reads), and only those owner bits are added: `chmod 000` becomes `0700` on a directory and `0600` on a file tego writes, `tego`'s own modes, and `0400` on the config layer, and no group or other bit is changed, since two checks judge those. The config trust check (identity-config.md R20) refuses a layer or a layer's directory that group or others can write, and the runtime directory's check (agent-contract.md R10a) refuses such a runtime parent, because someone else could have replaced what is in it; a restore to `0700` would have passed them over a directory that was writable to others until then. Each object is opened `O_PATH|O_NOFOLLOW`, so a link at its name is neither followed nor changed, and its mode is changed through the descriptor's `/proc/self/fd` link, so it lands on the object checked. Each mode restored is one `gap what=record why=own-state-mode-restored` naming its path in `binary` (spec/record/v1); `tego run` warns of the ones it restored before the run (`[own-state-mode]`), and the receipt, `status` and `drift` read the lines as no lost action (`gaps.Restored`). A root launcher restores none: it reads and writes through any mode. Its agent cannot take the modes of the run's own directory, which stays root's `0700` until `Close` hands it to the user (the hand-over rule above), and a root launcher makes no runtime directory; what that agent can take is the user's state above (`~/.tego` and what is in it, the ledger root, `.live`), which the user's next unprivileged `tego run` restores at its start. Until then that user's own `status`, `events` and dashboard cannot read it, so a user who launches only as root (`sudo tego run`, `adopt`, the guard) restores it by hand. Not restored: a group or other bit, as above, so an agent that makes `~/.tego` or the config layer writable to others still has every later run refused, with the check's own fix (`chmod g-w,o-w`), and one that does so to the runtime parent every later run that routes Codex (the others run without a runtime directory, so with no `TEGO_REASON`); a link at one of these names (the file or directory it leads to keeps the mode the agent gave it); what is not tego's own: the home itself, `$XDG_RUNTIME_DIR` itself (at `0000` it has every later run refused, `[run]`, since no runtime directory can be made in it), a configured ledger root's parent unless it holds `chain.log` (an account with no usable passwd home anchors beside its ledger root, so that parent is the anchor's directory and is restored as such), and the files the user writes that tego only reads (a `$TEGO_CONFIG` outside `~/.tego`, the price table, the profiles and the contract registry), whose taken mode makes a run that needs them fail or warn, naming the file; a run's own directory while the run lives, which its agent can still keep `tego status`, `events` and `stop` out of until the run ends; an earlier run's directory, whatever ended it, the run directory of a run whose launcher died included, since neither the sweep that ends an orphan nor a later run restores it (`events`, `receipt` and `gc` then cannot read it); a directory inside the run's runtime directory (its `CODEX_HOME`), which keeps that runtime directory from being removed until logout; and a mode another live run's agent takes again between a run's restore and its use. Since a run's end gives the config layer and `tego.log` back, what an agent took from them is not left for the commands after its run. What a run's end cannot give back is a mode taken while a run is still live (a 24/7 agent's), by a root launcher's agent, or by one whose launcher died: `tego run` and `tego gc` give those back before they read the config (`gc --dry-run` changes no mode), and every other command (`status`, `stop`, `events`, `receipt`, `compile`, `doctor`, `drift`, `ask`, the dashboard) reads the config warn-and-skip and passes over a layer it cannot read, with a warning, so until one of those two runs it goes by the other layers and the built-in settings, the built-in ledger root included; `gc`, which removes by the config's `retention` and `ledger_root`, refuses a layer it still cannot read and removes nothing (limits-check-doctor-cli.md R29).

`internal/ledger` owns all of the above except `tego.log` (`docs/OPERATIONS.md`). Concurrency: exactly one `Writer` per run directory for the run's lifetime, guaranteed by `flock`; any number of `Reader`s may open the same `events.jsonl` concurrently with the live Writer (read-only `open(2)`, no lock taken).

## 4. Functions and contracts

**`Open(dir string, run record.RunRef) (*Writer, error)`** — Pre: `ledger_root` exists and is writable; `run.ID` matches `RUN-IDENTITY.md`'s shape. Steps: reach the ledger root by the §3 walk (creating it as `MakeDirs` does), `mkdirat` the run directory `0700` if missing and open it, keeping that descriptor until `Close` (with `WithFreshRunDir()`, refuse with `os.ErrExist` a run directory this process does not own or that holds anything); open/`flock(LOCK_EX|LOCK_NB)` `lock` (on `EWOULDBLOCK` → `ErrRunLocked`); open `events.jsonl` `O_WRONLY|O_CREAT|O_APPEND,0600`; `mkdir blobs/ 0700`; copy the compiled contract to `contract.yaml` (best-effort, never fatal). Every name is opened relative to the run directory's descriptor, `O_NOFOLLOW`, and must be a regular file (with one link, for root) (§3). Post: `*Writer` has `seq==0`, `prevID==""`, no line written yet. Errors wrapped `%w` (`ErrRunLocked`, `*PathError`). Not idempotent across processes; no timeout (`LOCK_NB`, no retry), with one exception: with `WithFreshRunDir()` an `EWOULDBLOCK` is retried for up to 50 ms. The directory is this process's and has no holder, so the only other flock is a probe's (`gc`'s `lockFree`, `stop`'s liveness check), held for an instant, which would otherwise refuse a brand-new run with `ErrRunLocked`. A resumed run, where a holder is a live launcher, fails at once. `Open` is also a resume operation: on a directory that already holds a valid chain with no `run_end`, it continues `seq` and `prevID` from the last complete line and truncates an undecodable unterminated tail under the exclusive lock, recording a gap event for the loss; that path is what `RunRepository.Lock` and `gc`'s sweep use on a lost run.

**`(w *Writer) Append(e *record.Event) error`** — Pre: `e.V==1`, `e.Kind` valid; caller has set `Kind`, `Source`, `PID`, `TID`, `Cgroup`, `Rule`/`Verdict`/`Authority`/`Attr`, `Payload`, may set `MonoNS` to its own capture reading, and must NOT set `Seq`/`ID`/`Prev`/`Run`/`Agent`/`TS` (overwritten unconditionally). **`MonoNS` is stamped only when zero**: a producer's reading is the `CLOCK_MONOTONIC` time the event was captured, which is what §2's field doc and `enforce-cgroup-observe.md` E20 promise (the kernel recorder's `bpf_ktime_get_ns()`, the forwarder's request start), and overwriting it would record how long the event waited in the pipeline instead. Zero is E20's "unknown" and gets the append-time reading. Lines are therefore not guaranteed to be in `mono_ns` order along `seq`: kernel, forwarder and supervisor lines carry their capture time (the supervisor's is its notification's receipt, supervisor.md R23a, *amended 2026-10-16*; it was the time the pipeline stamped them) while lines with none carry the append time, and lines of different threads or sources reach the pipeline in arrival order. One thread's supervisor lines are in the order of its syscalls along `seq` and by `mono_ns` (supervisor.md R23a), with the two exceptions that rule names: a line whose previous line of the same thread was still unwritten after the supervisor's 1 s bound is written without it, and counted in `run_end.supervisor.order_lost`; and a notification whose previous one was not answered at receipt (its thread was released by a signal, E35) is not ordered after it. R7 makes `seq` the only ordering key, `measure`'s wall (limits-check-doctor-cli R21) takes the largest reading, and `status` measures idle from the largest `mono_ns` of a non-gap line (`limits-check-doctor-cli.md` §5 Views). `measure`'s idle max (limits-check-doctor-cli R22) still measures each gap from the previous line's reading, so after a line whose capture-time reading is older the next gap is counted from that older reading and overstates idle by the capture latency (the queue's backlog, under load); that stays an open condition in `limits-check-doctor-cli.md` §11: `measure` is to compare against the largest reading seen so far. **`Append` trusts `Payload` as already redacted and blob-split** — those are pipeline `Stage`s this package exports (`RedactStage`, `SplitBlobsStage`) that `internal/runtime` composes ahead of the `Sink` chain reaching `Append` (`docs/P0-DESIGN.md` §2.10, `docs/REPO-LAYOUT.md`); `Append` itself does not re-run either (I2 covers what that implies). Steps (`w.mu` held): stamp `Run`/`Agent`, `TS`, and `MonoNS` when zero; `Seq = w.seq`; `Prev = w.prevID`; `MarshalLine` once (the id is patched into the line in place, byte-identical to a second serialization, R2); one `write(2)`; on success only, `w.seq++`, `w.prevID = e.ID` and `w.size` advance. A failed or cut-back write leaves all three unchanged, so the next line reuses the seq and the chain has no gap (I4, E6). Post: on `nil` error the line is page-cache-durable (no fsync); `*e` now carries its assigned fields. Errors: `ErrShortWrite` after exhausted retries (E5); wrapped `ENOSPC` (§7); a marshal error is a programmer error, returned, never dropped. Exactly one `write(2)`; never `fsync`s. Not idempotent; safe for concurrent callers within one process (`w.mu`), though the product's pipeline drains one channel into `Append` from a single goroutine (`docs/P0-DESIGN.md` §2.4) so the mutex is a safety net.

**`(w *Writer) RedactStage(next Sink) Sink` / `SplitBlobsStage(next Sink) Sink`** — each returns a `Sink` closure performing its transform then calling `next`. `RedactStage`: allow-list `anthropic-version, request-id, content-type, user-agent, traceparent, tracestate`; unconditionally strip `x-api-key, authorization, cookie, proxy-authorization` (case-insensitive, any casing/duplicate), identically for `source: ssl` and `source: forwarder` — "never persisted, on the loopback leg too" (`docs/P0-DESIGN.md` §2.10). `SplitBlobsStage`: R10 (any payload field's JSON value over 4 KiB replaced by its sha256 via `w.Blob`/`w.BlobFrom`). `internal/runtime/run.go` is the only composition site: `Compose(stampRule, attributeStep, w.RedactStage, w.SplitBlobsStage)(w.Append)`. A caller reaching `w.Append` directly (a test, a future bug) bypasses both — I2 covers how that gap is handled.

**`(w *Writer) Blob(b []byte) (sha string, err error)` / `BlobFrom(r io.Reader) (sha, int64, error)`** — stream sha256 into `blobs/.tmp-<random>`, both names relative to the `blobs/` descriptor the Writer holds (§3); `Has(sha)` (stat) first to skip on a hit; on a miss `O_CREAT|O_EXCL,0600` then `renameat2(RENAME_NOREPLACE)` onto `blobs/<sha256>` (a plain `rename(2)` where the filesystem lacks the flag); on `EEXIST`, a duplicate already there, discard the temp file and leave the existing blob in place (its inode and fsync state untouched); and treat as success — **without re-reading the existing target to confirm it hashes to `sha`** (R14, E28). Idempotent for identical content. Errors: `ENOSPC` (§7).

**`(w *Writer) Close(reason record.RunEndPayload) error`** — Pre: `reason.head` left empty (no parent run in P0). Steps: build+`Append` the `run_end` event (its assigned `ID` becomes `w.headID`, distinct from the payload's own `head` field, R13); fsync the blobs written since `Open` (for a run `Open` resumed, every blob in `blobs/`, by one `syncfs`, since the dead writer's lines name blobs this store never saw written), **then** `file.Sync()` on `events.jsonl` (the run's one durability barrier, in that order — a line carrying `blob:"<sha>"` is a pointer, and no blob is fsynced before this point, so syncing the ledger first would make every reference of the run durable while the bytes they name are still page cache: a crash inside `Close` would leave a ledger that verifies and reads as `ended` with its captured bodies gone and no `gap` recording the loss, where the reverse direction leaves at worst an orphan blob `gc` removes with the run directory; both syncs are attempted even when the first fails, so one cannot cost the other its fsync); `ChainAnchor.Append(w.ref.ID, w.headID)` once `events.jsonl`'s fsync succeeded, whatever the blobs' said, since the anchor vouches for the chain and `Verify` never reads a blob (withholding it would leave a durable chain reading as `ErrAnchorMissing` forever); `Close` reports every error joined; close the blobs fd; `flock(LOCK_UN)` and close the lock fd; last, when the process is root and the ledger root is another uid's, hand the run directory over through the descriptor `Open` kept, walking it only when this process owns it (§3 hand-over rule; a failure there is logged, not returned — the run is complete and only who may read it is left undone); then close the run and `blobs/` directory descriptors. Post: `events.jsonl` ends fsync'd with `run_end`; `chain.log` has a new anchor line; lock free. Errors: `run_end` is encoded at the run's revision before anything is closed, and one the Writer refuses (`record.ErrInvalidEvent`: an unknown `reason`, a `stopped_by` malformed, on a `run_end` not `stopped`, or below the run's record minor) is returned with the Writer still open, its lock and descriptors held and nothing written, so the caller closes again with a `run_end` it can write and the run keeps its `run_end`, fsync and anchor (*added 2026-10-25*); a write failure during `Close` is returned but the lock/fds are still released. **A `ChainAnchor.Append` failure after a successful `Sync()` is returned distinctly as `ErrAnchorWrite`**, not folded into an `Append`/`Sync` failure — the run is already durable and terminal at that point (§7, E29), and callers must be able to tell "run fine, anchor missing" from "run's own tail incomplete." Not idempotent: a second `Close` returns `ErrAlreadyClosed`, writes no second `run_end`. `Abandon()` is the close of a run that never started, and what the launcher's unwind calls: it releases the lock and every descriptor and writes nothing — no `run_end`, no fsync, no anchor, no hand-over — and a later `Close` or `Abandon` is `ErrAlreadyClosed`. `Close` there would append `run_end` as line 0 of a ledger with no `run_start`, and a launcher killed before it removed the directory would leave a run that read as ended rather than empty.

**`Open(dir string) (*Reader, error)`** (read side) — `dir` need not yet have `run_start`. `open(events.jsonl, O_RDONLY)`, no lock. `os.ErrNotExist` if absent.

**`(r *Reader) Iter() iter.Seq2[*record.Event, error]`** — yields every complete, valid line in order. A line failing to parse as the **last** line **and** missing its trailing `\n` is "torn": iteration ends cleanly, no error — unless the line before it is `run_end`, which no dying writer writes before a torn line, so bytes after it are `ErrCorruptLedger` naming their byte offset, as `Verify` refuses them. Anywhere else, a parse failure yields `(nil, err)` and stops, naming the line and its byte offset; `v != 1` yields `ErrUnsupportedVersion` the same way, except that a reader set by `SkipNewerVersions()` (the views,
`limits-check-doctor-cli.md` §6 case 20) skips a line whose `v` is an integer above 1 and counts it
(`SkippedNewer()`, the largest count of any one pass). `Entries()` is `Iter` with each stored line beside its event. No mutation across calls — each `Iter()` rescans from byte 0; a live run is tailed by `Follow` (below), which reads each byte once. Safe from multiple goroutines/processes on independent `*Reader`s, including against a live `Writer` (E19).

**`(r *Reader) Backward() iter.Seq2[Entry, error]`** (*added 2026-10-16*) — the lines `Entries` yields, last first, read
from the end of `events.jsonl` in 16 KiB blocks (a line longer than a block widens the read, never past
`MaxLineBytes`), so a caller that stops at the newest line it wants reads the lines after it and not the ledger:
`tego events --last` (limits-check-doctor-cli.md R29). It applies `Iter`'s rules unchanged: an unterminated last
line is a line only when it decodes, a torn tail is passed over unless the line before it is `run_end` (then
`ErrCorruptLedger` naming the tail's offset), a line that does not decode is `ErrCorruptLedger` naming its line
number and offset, a newer version's line is skipped and counted under `SkipNewerVersions()`, and a line past
`MaxLineBytes` is `ErrCorruptLedger`; the line number in an error is counted from byte 0 when the error is reported,
the one time it reads before the line. The file is read up to the size it had when the call started, by positional
reads, so a line a live `Writer` is appending then is never taken for one (E19). What it does not reach it does not
check: damage before the line a caller stops at is not reported, as `State` does not report it; `Iter` and `Verify`
do (`TestBackwardReadsWhatEntriesReads`, `TestBackwardStopsReadingAtTheCallersLine`). The ledger stays the one store
(ADR 0004): no index or cache of positions is kept beside it, and the file is never rotated, so the end of the one
file is the newest record.

**`ChainAnchor.Append/Head`** — `Append` is one `write(2)` of `"<run> <head>\n"`, same R4 atomicity argument since `chain.log` is also local and `O_APPEND`. `Head` is a linear scan tolerant of a torn last line by the same rule as `Reader.Iter` (E28) — verification tooling only, never on a run's hot path. A run is anchored once, at `Close`, so two lines for one run that name different heads are `ErrCorruptLedger` (Verify: unverified), not "the last line wins", which let an appended line re-anchor a truncated ledger; the same line repeated is the same anchor. Both reach the directory through the §3 walk and open the file `O_NOFOLLOW|O_NONBLOCK`, refusing anything but a regular file (with one link, when root): `chain.log` lives in the user's directory, and a root launcher appending through a planted link — at the file, or at `~/.tego` itself — would write into any file on the machine. A `chain.log` this call creates has its directory fsynced (through a readable descriptor: fsync refuses the walk's `O_PATH` one), and a failure there is returned. `ProbeAnchor(path)` is `Append`'s open without the write: `~/.tego` and an empty `chain.log` are created if missing (handed over as `Append` would: only what the call created, `chain.log` by an `O_CREAT|O_EXCL` open), and `tego run` calls it before the run directory exists, so an anchor the run could not extend at `Close` refuses the run up front (`runtime-launch.md` case 37, §7) instead of surfacing as `ErrAnchorWrite` after the agent ran. `Close` can still meet E29 (a disk that fills while the run is live); the probe removes only the failures that were already there.

**Where a swept orphan is anchored.** A sweep ends a run whose launcher died (`gc`, and the sweeps inside `run` and `stop`), and appends its head where that run's own launcher would have: the sweeper's own anchor for its own runs; for a run directory another account owns — which on a shared ledger root means a root sweep, since only root can take another account's run lock — that account's `~/.tego/chain.log`, or, when it has no home, the chain.log beside this ledger root. The owner is read from the filesystem, never from the ledger: the run directory's uid, or the ledger root's when root owns the run directory (a root launcher that died before handing it over). A run the owner cannot be told for — root owns both the run directory and the ledger root, as for a `sudo tego run` on an operator's `/var/lib/tego/runs` — is anchored in the sweeper's own chain.log, and its owner's `events --verify` then reports `ErrAnchorMissing` (exit 1) until it is verified from the sweeping account. That is stated, not repaired: nothing outside the ledger names the account such a run belongs to, and the ledger's own content — which the run's agent may have shaped — is never what chooses the file root appends to.

**`(r *Reader) Verify(ctx, anchor ChainAnchor) (VerifyReport, error)`** — the run verified is the one the run directory names (every directory a ledger root holds is named by its run id; for a copy under another name, the first line's id), the name being the one the path gives the directory (`ledger.RunDirPath`): the last component of the path made absolute and lexically cleaned, never resolved when it is a run id — `<ledger_root>/<A>` replaced by a link to `<ledger_root>/<B>` is A's record gone and verifies as A, `ErrRunMismatch` against B's lines (or `ErrLedgerMissing` when the target holds no ledger), never as B's anchored ledger — while a last component that is no run id, such as a link `~/latest`, is followed one link at a time to the first name in the chain that is a run id, a relative target read from the directory holding the link. A relative path starts from the working directory as `$PWD` names it when `$PWD` is that directory, so `cd <ledger_root>/<A> && tego events . --verify` names A even when A is a link; with no such `$PWD` it is the kernel's path, which names the link's target (so `cd <run> && tego events . --verify` names the run, and a deleted ledger reached through `.` is `ErrLedgerMissing`, 1; symlinks are not resolved before the name is taken, or a run directory replaced by a link to another anchored run's directory would verify the other run's ledger clean), and every line must carry that id (`ErrRunMismatch`), with the anchor looked up under it, never under an id the ledger supplies (or another anchored run's ledger copied over this run's `events.jsonl` would verify clean against the other run's anchor line). It walks the chain from byte 0: every complete line re-hashed against its `id` (R2), `seq` gapless and `prev` linked (I3, I4), every event validated —
a line of a newer record version is linked (`record.Chain.AddNewer`: its bytes re-hashed, `seq`, `prev` and `run`
checked) and counted in `VerifyReport.Newer`, its content not validated; its `kind` and `seq` are chain fields all the same, so a newer `run_start` at seq 0 is the run's start and a newer `run_end` its end (`Started`, `Ended`, a line after it refused); a torn last line is skipped and reported (`TornBytes`). An unterminated last line of a newer version that is otherwise whole (chain fields read, id the digest of its bytes) lost only its `\n` (E8) and is a line, like the same line terminated; the views, `lastLine` and `Verify` agree, and `Writer.resume` refuses it rather than truncating it. `Verify` also refuses a run whose shape is wrong even when its chain is intact: line 0 must be `run_start`, `run_start` may appear nowhere else, and no line may follow `run_end` (`ErrUnverified` naming the line); `Writer.resume` refuses a ledger with a line after `run_end` (`ErrRunEnded`). With an anchor, the head is checked against `chain.log` **whenever it holds a line for the run**, not only when the ledger still ends in `run_end`: the anchor is written once, at `Close`, with the `run_end` line's id, so an anchored head the ledger does not end with is a ledger that lost lines after it was closed (unless the scan ended short of `run_end`, or inside one: a launcher's `Close` may have landed between the scan and the anchor read, so `Verify` rescans once and reports the mismatch only if it survives) — a truncation that removes `run_end` and the events before it leaves a chain that is internally intact and reads as `lost`, and only the anchor tells it from a launcher that died. An ended run with no anchor line is `ErrAnchorMissing` (E29) unless its lock is held: `Close` anchors last with the lock held, so `Verify` re-reads the line while the lock is held (up to 2s) and, if it is still held, returns `ErrRunClosing` ("run is closing, retry"; not `ErrUnverified`, exit 125). A run that has not ended owes none. A torn tail is tolerated only on a run that has not ended: `Close` writes `run_end` last and fsyncs, so bytes after `run_end` are not a crashed writer's (E6) and the ledger does not verify. Every finding about the ledger's content wraps `ErrUnverified`; a read error does not, so a caller can tell "this ledger is not what was written" from "it could not be read". A finding that is a line's own (a line that does not hash or chain, fails validation, belongs to another run, follows `run_end` or is too long) names that line in `VerifyReport.AtLine` and `BrokenLine`, its seq, even when the line chained and is counted in `Lines`; a finding made once every line was read (the anchor, bytes after `run_end`) or with no ledger to read names none (*added 2026-11-02*). `VerifyRunDir(ctx, dir, anchor)` is `Verify` over a run directory, plus the cases a `Reader` cannot reach: when `events.jsonl` has been swapped for a link, a FIFO or a directory (which `OpenReader` refuses on purpose) and the anchor holds a line for the run, that is `ErrUnverified` (exit 1), not a read failure; when `events.jsonl` (or the whole directory) is gone and the anchor holds a line for the directory's run id, that is `ErrUnverified` with `ErrLedgerMissing` — the anchor says the run was recorded and closed — while no ledger and no anchor line is the plain not-exist error (nothing says the run ever existed). An empty `events.jsonl` under an anchored id is the anchored-head mismatch above. `tego events <run> --verify` is the command (`limits-check-doctor-cli.md` R29). A run anchored before 2026-09-22 under a `ledger_root` other than the default has its line in `<ledger_root>/../chain.log`, where the anchor then lived, and verifies as `ErrAnchorMissing` against `~/.tego/chain.log`; for the default `ledger_root` the two files are the same one.

**`RunRepository.List/Open/Lock/State`, `BlobRepository.Put/Get/Has`** — `List` skips non-run-shaped entries, returns partial results plus a wrapped error on the first unreadable one; `Lock` (what `run`/`stop`/`gc`'s orphan sweep calls) fails fast (`LOCK_NB`) and resumes only a run directory that exists (`WithExistingRunDir`: a missing one is `os.ErrNotExist`, never recreated, so a sweeper that lost a race with `gc`'s removal writes no ghost ledger; the sweep reads it as not its to end); `State` never blocks (it probes the lock first, then reads the tail: a Writer appends `run_end` before it releases the lock, so a lock seen free makes the tail read final; `EWOULDBLOCK` → `StateRunning` unless the tail already holds `run_end`; success+unlock → `StateLost`/`StateEnded` by whether `run_end` was found) and reads only the **end** of `events.jsonl` — the last complete line and the lock are the whole definition, and `gc` asks every run directory for its state, so decoding whole ledgers here would make its cost scale with everything retention has not yet removed. One consequence is deliberate: damage *before* the last complete line is `Verify`'s to report, not an error from the state probe; an undecodable *last* line is still `ErrCorruptLedger`, since the state itself cannot be read then. A newer-version last line whose chain fields read is not undecodable: it is read as `Verify` reads it (`record.LinkOf`), so a newer `run_end` is `StateEnded` and any other newer line is a line present, and `agentOf` skips a newer-version first line and leaves the agent to the contract copy. `tego run` and `tego stop` do not ask every run directory: they sweep the runs the live index names (`SweepLive`, §3), and only `gc` walks them all. A tail-only `State` keeps that walk linear in the number of runs rather than in their size, and keeps an index entry's cost to one tail read.

**`gc(root string, keep time.Duration, dryRun bool) (Report, error)`** (package-level, called by `internal/cli/gc.go`) — `List` every run; `StateRunning` → skip, always; `StateLost` → sweep (lock, `cgroup.Kill` if populated, `Append run_end{reason:"orphaned"}`, `Close`) before considering deletion; age is computed from the run id's embedded `time36` when parseable, falling back to the last event's `ts` only otherwise (R16, E30 — `ts` alone is unsound here per R7); `age > keep` → the run directory is removed through the ledger root `gc` opened once, before listing (`os.Root.RemoveAll(<run id>)`), so a path component swapped for a symlink after the listing cannot send a root-run removal outside `ledger_root`. `List`, `State`, the lock probe and the sweep's lock and `run_end` append still go by path, so before each removal `gc` checks that `ledger_root` still names the directory it opened (`os.SameFile`) and otherwise reports the run and removes nothing: a decision read from a decoy put at the path is never applied to the held root's same-named run, a live one included. A swap made and undone between the decision and that check is not detected; the path-based steps are only as sound as `ledger_root`'s parent directories. Every run directory ends up untouched or fully removed; a surviving run's `events.jsonl` is byte-identical to before. Errors aggregate per run (joined when one run fails twice, e.g. an unreadable state and then a failed removal) into `Report{Deleted, Kept, Swept []string; Errors map[string]error}`; one run's failure never aborts the others. An error names its path under the configured `ledger_root`, never the `/proc/self/fd/<n>` name of the root descriptor the pass holds, which names nothing once tego has exited; `SweepLive`'s errors likewise (*amended 2026-10-05*). A run whose `State` cannot be read at all (an unreadable `events.jsonl`, a read error) is reported **and still aged out**: it is never swept — nothing may append `run_end` to a ledger nothing can read — and its age comes from `runTime`'s `time36`/mtime fallback, so retention stays the real bound on `ledger_root`. Liveness is the one exception: a lock that is held, or that cannot be probed, keeps the directory whatever its age. `gc` never prunes `chain.log`: the anchor line of a run it removed stays (about 90 bytes a run), so `tego events <run> --verify` on an aged-out run reports `ErrLedgerMissing`, the same finding as for deleted evidence, since a removal by retention cannot be told from tampering. Re-running `gc` immediately is a no-op. *Added 2026-10-26:* the same pass, at the machine's `retention`, also runs at a `tego run` start at most once per the machine's `gc_interval` (off by default), for at most 2 s, under the flock of the ledger root's `.gc-stamp`, whose mtime is when the last pass began; `gc` with no `--keep` and no `--dry-run` takes the stamp too (`internal/cli` `retainBeforeRun`, `TestRunStartAppliesRetention`). A stamp the caller may not open (a root pass died before handing it to the ledger root's owner, or its chown failed) is unlinked and made again once it is due, and left alone inside the interval (`TestRetentionStampNotOursIsReplaced`); it only spaces the passes, and two that overlap are kept off each run by that run's lock. A run that reads `StateEmpty` (the lock free and no complete line: its launcher died between `Open` and `run_start`) is not only aged out. Its cgroup may already exist, and nothing else would remove it (3 of 40 random launcher kills left an empty ledger and a scope behind). Such a directory is almost never an unwind's: unwind removes the run directory right after `Abandon`, so it is a launcher killed between `MakeRunDir` and `run_start`, whose child was held before the Ack and never exec'd the agent. Outside a dry run, the sweep hook runs for it before retention is considered, under the run's lock (taken without blocking, the run re-checked empty under it; a held lock or a missing lock file skips it, so a live launcher between `MakeRunDir` and `Open` is never killed), with the agent named by the top-level `name:` line of the contract copy `Open` wrote (validated as an agent id). With no contract copy, or one that names no agent, the hook does not run, since there was no cgroup yet. Nothing is appended to its ledger, because a run that never started has nothing to end. A hook failure keeps the run whatever its age, as it does for a lost run. A lost run whose sweep did not run (its lock was held past a short wait, or it became live) is kept whatever its age unless it reads ended by then, so a probe's instant hold cannot delete an orphan's record before its hook ran. A lost run whose first line does not give its agent takes the agent its contract copy names, as an empty run does; with neither, its sweep is an error, reported per run, and the run is not counted in `Swept` (`TestGCDoesNotCountALostRunItCouldNotSweep`). An ended run is never touched by `gc`, which has no live index: the anchor and scope of an ended run whose launcher died before clearing its entry are `SweepLive`'s (§3 Live index). A lost run another host minted (`WithForeignRun`) is never swept — no hook, no `run_end` — but it ages out past `keep` like an ended or empty run, removed under its lock as any run is; one whose lock is held here is kept. Retention matters here because a machine id that changes (a reinstall keeping `/home`, a cloned image, the hostname fallback with a renamed host) makes every run of this host foreign for good. `SweepLive` clears its entry once its directory is gone, and `tego doctor` counts the runs of each other host (`limits-check-doctor-cli.md` R27).

**`Follow(dir string, from Cursor) (*Follower, error)` / `(fl *Follower) Lines(ctx) iter.Seq2[FollowEntry, error]`** (*added 2026-10-24*; the one follower in the lowest layer, which `tego events --follow` reads and other readers are to use rather than keep their own) — opens `events.jsonl` as `OpenReader` does (`O_RDONLY|O_NONBLOCK|O_NOFOLLOW`, regular files only, no lock; `os.ErrNotExist` when absent), so any number may follow a live run. `Lines` yields each complete line after the cursor once, in order, as `Entries` would (the stored bytes and the decoded event), each with the `Cursor{offset, seq, id}` that names it: the byte offset where the line starts, its seq and its id. It reads with positional reads from the first byte it has not delivered into one buffer of 32 KiB that grows, for a longer line, to at most `MaxLineBytes` and goes back to 32 KiB once what it holds fits there, that is once the long line is delivered (`TestFollowerGrowsForALongLine`). Only the bytes before the first undelivered one are fixed (E19 holds below it): a Writer that resumes a lost run (the reaper, a run's, `stop`'s or `gc`'s orphan sweep) truncates the torn tail a follower may be holding and appends after it, under the lock, so the undelivered bytes are read again on every read, never kept across one (`TestFollowerRereadsATornTailAResumeTruncates`: a held torn tail joined to the lines that replaced it read as a break in a ledger that has none); it keeps no line once the caller has moved past it (`Entry.Line` is that buffer, valid until the next line), so its memory does not grow with the run (`TestFollowerMemoryFlat`: 1,000,002 lines, about 250 MB, with the heap in use under 32 MiB over its start — 3 MB measured — and the buffer at 32 KiB). Every line is checked as it arrives by the check `Verify` makes (one `runCheck` both use): its id against its bytes, seq gapless and prev the line before (I3, I4), the run directory's id on every line (`ErrRunMismatch`), `run_start` line 0 and only line 0, nothing after `run_end`; `Verify` also validates each line's schema and checks the anchor, the follower decodes as the views do. A break ends the sequence with `ErrCorruptLedger` naming the line (counted from 1) and its byte offset, and nothing after it is delivered (`TestFollowDetectsTamperedAppend`). A newer record version's line has its link checked and then ends the follow as `ErrCorruptLedger`, as it ends `Entries`, unless `SkipNewerVersions` is set, when it is skipped and counted (`SkippedNewer`), and a resume from a cursor before it skips it again (`TestFollowerNewerVersionLine`). An unterminated last line is held while a writer holds the lock, since a reader can see one `write(2)` half done; once the lock is free it is a line if it reads as one (`wholeLine`, E8) and a torn tail otherwise (E6). The lock is probed before the read that finds the end of the file, as `State` probes it, so a lock seen free means that read was final (`TestFollowerLockSeenFreeMeansTheReadWasFinal`: a `run_end` appended and the lock released between the read that found no more and the probe is delivered, never `ErrRunLost`). The sequence ends: cleanly after `run_end` once the lock is free (a launcher anchors after `run_end` with the lock held, so the follower waits it out); with `ErrCorruptLedger` for a line or bytes after `run_end`; with `ErrRunLost` (which `tego events --follow` reports as `[run-lost]`) when the lock is free and there is no `run_end` (a lost run, or a launcher that died before `run_start`; the next sweep ends it as orphaned); with `ErrCorruptLedger` for a line past `MaxLineBytes`; and with the context's error. It wakes on inotify (`IN_MODIFY` on `events.jsonl`, `IN_CLOSE_WRITE` on `lock`, which the Writer's `Close` raises when it releases the lock), with the poll interval of 1 s as a backstop; when inotify cannot be had (`inotify_init1` fails with `EMFILE`, `fs.inotify.max_user_instances` spent; `inotify_add_watch` fails with `ENOSPC`, `max_user_watches` spent; or any other refusal) it polls every second and `Wake()` says `poll` and why. `OnIdle(fn)` runs `fn` each time every line there is has been delivered and the follower is about to wait: a renderer flushes there. A follower started from a cursor first reads the line at the cursor's offset: the byte before it must be `\n`, the line must be complete or the whole unterminated last line of a ledger no writer holds (E8, which the follower delivers too: a follower resumed from it ends there, cleanly after `run_end` and with `ErrRunLost` otherwise; `TestFollowerResumesFromAnUnterminatedLastLine`), a partial line there while a writer holds the lock is waited for (`TestFollowerResumeWaitsForAPartialCursorLine`), and so is the whole unterminated last line while the lock is held, since its holder may yet terminate it and append after it, the lock probed before the last read as `Lines` probes it (`TestFollowerResumeWaitsWhileTheLockIsHeld`: neither `[cursor-mismatch]` nor `ErrRunLost` while a resuming Writer holds the lock; `TestFollowerResumeLockSeenFreeMeansTheReadWasFinal`: a Writer that terminates the line, ends the run and releases the lock between that read and the probe has its lines delivered), and it must carry the cursor's seq and id (its id checked against its bytes); otherwise `ErrCursorMismatch` (`[cursor-mismatch]`) and nothing is delivered, since the lines skipped are unchecked. The chain then resumes after that line (`record.ChainAfter`), so a resume costs one line, not the run. Rejected: a follower in `internal/check` or in each service that reads a ledger (one follower, in the lowest layer, so every consumer gets the same chain check and the same torn-line rules); re-running `Reader.Lines` from byte 0 on each wake (quadratic in the run's length); a cursor of `seq` alone (a resume would rescan from byte 0 to find it) or of the offset after the line (its id could not be checked without reading backwards); inotify alone (a file replaced under its name, or a filesystem that raises no event for another mount's writes, would hang the follower; the 1 s backstop bounds that to a delay); trusting an unterminated last line while the lock is held (a half-done `write(2)` whose cut falls just before the `\n` would decode); keeping the undelivered bytes across a read and reading only past them (a resume's truncation of a torn tail is then invisible, and the stale bytes join the new line: a false `[ledger-corrupt]` on an untampered ledger); detecting the truncation by size alone (a resume that truncates and appends can leave the file longer than it was).

**`WatchLive(root string) *LiveWatch` / `(lw *LiveWatch) Changes(ctx) iter.Seq2[LiveChange, error]`** (*added 2026-10-24*) — reports the runs entering (`LiveEntered`) and leaving (`LiveLeft`) the live index of a ledger root (§3 Live index), reading the index's names and nothing else, as `SweepLive` does: the root is reached by the §3 walk, the index opened `O_NOFOLLOW` (a link is `ErrLinkRefused`), an entry that is no run id passed over, no entry opened. A root or an index not made yet lists nothing until it is. It follows at most `MaxLiveFollowed` = 512 runs: the names are read 256 at a time, and a scan keeps the followed runs and at most 512 candidates, so its memory is bounded whatever the index holds; the runs listed past the bound are counted and reported (`LiveExcess`, whenever the count changes), never dropped without a word, and taken up as followed runs leave (`TestLiveWatchFollowsAtMost512`). It wakes on inotify on the index (on the root while there is no index) with the same 1 s backstop and poll fallback as the follower. An index that cannot be read ends `Changes` with that error. A run that leaves and returns between two scans is not reported; its Follower is what tells a consumer that a run ended.

**`MarkLive(root, id string) error` / `ClearLive(root, id string) error` / `SweepLive(ctx, root string, opts ...GCOption) (Report, error)`** (*added 2026-09-24*, the live index of §3) — `MarkLive` lists a run: the index directory is reached by the §3 walk and created `0700` when missing, the entry is created `O_CREAT|O_EXCL|O_NOFOLLOW|O_NONBLOCK` `0600`, both handed over under the hand-over rule when root creates them in another uid's directory; a name already there lists the run as well (nil); a malformed id is `ErrBadRunRef`. `internal/runtime` calls it in `openLedger`, after `Open` took the lock and before `run_start`, and a failure refuses the run (125). `ClearLive` removes the entry, by `unlinkat` in the index directory the walk opened, only when the run's directory is gone or its `State` is `StateEnded`; a missing index or entry is nil. Nothing but entries is removed. With no index, or one that cannot be read (reported under `Errors[".live"]`), it is `gc` with no retention. Its cost is the entries, not the runs: `BenchmarkSweepLiveNRuns` (internal/runtime) holds the same time at 10 and 1,000 sealed runs. Another host's entry is otherwise left alone, and cleared once its run directory is gone, which `gc`'s retention brings about for a foreign lost run too.

## 5. Business rules

**R1 — Canonical field order.** `MarshalLine` writes keys in exactly this order: `v seq id prev ts mono_ns run agent pid tid cgroup kind source rule verdict authority reason attribution <payload keys>`. Zero-value `omitempty` fields are dropped entirely. Pinned by an explicit writer function (`bytes.Buffer`), never struct-order `json.Marshal`, so a field reorder cannot silently change on-disk bytes.

**R2 — `id` computation.** `id = hex(sha256(line))`, `line` being the canonical serialization with `id` set to 64 `"0"` chars in position. After hashing, `id` is set to the real digest and the event is serialized **one more time** — those bytes are what `write(2)` sends and what a verifier re-hashes (with `id` zeroed again). One canonicalization function, called twice. This zero-placeholder convention is this document's choice, not spelled out byte-for-byte normatively — flagged in §11.

**R3 — Payload splicing, not nesting.** `Payload` (`json.RawMessage`, a JSON object) is spliced inline after `attribution`, sorted lexicographically for determinism (the §2.2 structs are already fixed-order, but `MarshalLine` sorts defensively since a caller could pass a `map`-built `RawMessage`).

**R4 — One `write(2)` per line.** `Append` builds the complete line in one buffer and calls `Write` exactly once. A single `write(2)` to a regular `O_APPEND` file is atomic for any length on Linux — torn-line tolerance depends on this. Linux-specific; `ledger_root` on NFS is unsupported (§11).

**R5 — Unknown-field tolerance and version gate.** `Decode` unmarshals into a permissive intermediate, never `DisallowUnknownFields` (`docs/VERSIONING.md` §2). `v` is checked first; anything but `1` returns `ErrUnsupportedVersion` before any other field is read, and an
integer `v` above `1` wraps `ErrNewerVersion` beside it (a line a newer binary wrote; `limits-check-doctor-cli.md`
§6 case 20).

**R6 — fsync policy.** `Append` never `fsync`s. `Close` calls `file.Sync()` once, after the `run_end` line's `write(2)` returns. A line `Append` reported successful survives process death but not a kernel crash/power loss before the next `Close` fsyncs — matches `docs/P0-DESIGN.md` §9 ("<20 µs, no fsync per event"). What such a crash leaves usually ends on a line boundary, so resume finds no torn tail, and the sweep's `Close` closes and anchors what survived: the chain verifies from `run_start` to `run_end` over a record that lost its end. The same goes for lines still in a killed launcher's queue. So every orphaned run carries `gap what=record why=launcher-lost`, no count, just before its `run_end`, written in `Close` for all of its writers (`gc`'s and `tego run`'s sweep, the reaper, an adopter's reap; *added 2026-11-01*); a gap that cannot be written leaves the run lost for the next sweep rather than end it with no gap. A verified orphaned run proves no line changed after it was written, never that it holds every line. Before `events.jsonl`, `Close` fsyncs the run's blobs, so no blob reference is ever durable before the blob it names (§4 `Close`). `Close` also fsyncs the directory entries that name the run: the run directory (which holds `events.jsonl`, `contract.yaml` and `blobs/`) and the ledger root it is in, since a file's fsync persists a new entry on ext4, XFS and btrfs in practice and POSIX does not promise it (a directory fsync that fails joins the blob errors, reported after the anchor; `EINVAL` from a filesystem that cannot fsync a directory is not a failure). The anchor's directory is fsynced when `chain.log` is created. `contract.yaml`'s temp file is fsynced before its rename, so a crash cannot leave the copy empty (drift and the sweep of a launcher killed before `run_start` read it); `last-refusal.json`, rewritten after refusals as a hint to the agent (§3), is not. `Open` removes the `.contract.yaml.*` and `.last-refusal.json.*` temp files a writer that died before its rename left behind, under the run's lock, as it removes partial blobs.

**R7 — Clock discipline.** `ts` (wall clock) may move backward or jump forward; no code may use it to order events or compute elapsed time within a run. `seq` is the only valid ordering key. `mono_ns` is monotonic only within one boot of one host. This binds `gc`'s own retention math too — see R16.

**R8 — Attribution presence.** `Attr` is populated for `Kind` ∈ {`exec`,`fs`,`net`,`mcp`}, empty otherwise. The writer produces `{unattributed,none}`, `{likely|unattributed,time,Step:N}`, `{likely,tid,Step:N}` or `{likely,tool_id,Step:N,ToolUseID}` (capture-derive R34, R42; `tid` and `tool_id` from `record_minor` 29, 2026-10-20, before which they were P1 and no writer produced them); `exact` is never written, though `Decode` accepts it, and accepts a `tool_id` attribution without a `ToolUseID` as v1 always has. `ToolUseID` under any other method is invalid (`Attribution.Valid`).

**R9 — Redaction is a pipeline stage, not part of `Append`'s contract.** The header allow/deny transform (allow `anthropic-version, request-id, content-type, user-agent, traceparent, tracestate`; unconditionally strip `x-api-key, authorization, cookie, proxy-authorization`, case-insensitive, both `source: ssl` and `forwarder`; the payload's own `headers` and `path` keys are matched as `encoding/json` matches them, by Unicode case folding and after JSON unescaping, and every spelling present is redacted where it stands, so `"Headers"` or `"path"` is no way around it; a payload with nothing to remove, including a `headers` object that already holds only allow-listed lower-case names, is left byte-identical rather than re-encoded body and all; only the payload's top level is walked and only its `headers` and `path` values are decoded, so an `ssl_request`'s inline body, which the blob split has not yet moved out, is never parsed here, and a rewrite splices the redacted members into the payload as written, every other member kept in place byte for byte, a payload that is not valid JSON being refused whole downstream by the blob split and `MarshalLine`) runs as `Writer.RedactStage`, composed by `internal/runtime`'s pipeline **before** `Append` (`docs/P0-DESIGN.md` §2.10: "Redaction stage before `Append`"; `docs/REPO-LAYOUT.md`: `Compose(stampRule, attributeStep, redact, splitBlobs)(ledger.Write)`). The logic is owned by `internal/ledger`; its *invocation point* is not — both once sat inside `Append` (I2 restates what is actually enforced).

**R9a — The request target is projected onto public routes before persistence.** A credential can appear in a path segment, query value, query name, or bare query component, including a very short one. `Writer.RedactStage` therefore reduces an `ssl_request`'s `path` to a fixed vocabulary: `*`, `/`, `/v1/messages`, `/v1/messages/count_tokens`, `/v1/chat/completions`, `/v1/responses`, `/v1/models`, `/v1/files`, and `/v1/messages/batches`. Every other path, including resource IDs and unknown provider routes, becomes `/redacted`. A query, even an empty one, becomes the single marker `?redacted`; no name, value, flag, or count of components survives. Absolute-form authorities and fragments are removed. Encoded or extended spellings of a static route do not inherit its allowance.

This policy preserves operation metadata for fixed public routes without trying to detect credentials in arbitrary client text. Forwarding and derive use the original target before the ledger boundary, so requests retain their routing and usage accounting. Both the uprobe and forwarder producers pass through the same redaction stage. Filesystem `exec` and `fs` paths remain unchanged, and bodies and allowed header values retain their separately documented recording behavior. The same holds for the `ask`, `answer` and first_write `refused` lines (agent-contract R22): their `target` is the human's grant, so a filesystem path or connect destination is stored exactly, and only a forwarder request target's path (`authority METHOD path`) is projected onto this vocabulary. `RedactTarget` is idempotent; the unit and fuzz regressions enforce its fixed output vocabulary and the short-secret reproductions.

**R10 — Blob split threshold.** Any payload field whose JSON value exceeds 4096 bytes (4 KiB) is replaced by its sha256 via `Writer.SplitBlobsStage` (same pipeline placement as R9; `WriteRunStartIn` applies the same split itself, so a `run_start.command` over 4 KiB is stored as `command_blob`); unchanged key where §2.2 already names one (`ssl_request.blob`), else `<fieldname>_blob`. Fields under 4 KiB stay inline. The reserved fields (`record.IsMVPField`) are never split, whatever their size (*added 2026-10-25*): in a blob neither the Writer's check nor Verify would read them, and a reader would find the field absent. The record bounds them instead (`record.MaxSecrets` and `MaxShares` 64 entries, `MaxRedactions` 128, a share path 4096 bytes), so a `run_start` with every list at its bound still fits `MaxLineBytes`. The fields are split in sorted key order, and a split's key is checked against every key the payload had and every key a split added, so a payload `{x, x_blob}` with both over 4 KiB is refused every time, never refused or split by map order.

**R11 — Message dedup is per-run, not global.** Within one run's `blobs/`, identical content is addressed once; across runs it's stored twice — no host-wide CAS, so `gc` deleting one run can never orphan another's blobs. Exact-content dedup alone does not dedup messages — every model request re-sends the whole conversation, so each request body is new content and a conversation of n turns would be stored O(n²), against P0-DESIGN §2.10's "`messages[]` items stored once by hash" — so conversations are spliced. An `ssl_request` body over R10's threshold that is one JSON object with exactly one top-level conversation member — `messages` (Anthropic, OpenAI chat), `input` (OpenAI Responses, which Codex sends) or `contents` (Gemini) — holding a non-empty array whose elements average at least 16 bytes each, separator included (an array of numbers or empty objects is stored whole, since one span and one hash per element cost the recorder's one pipeline goroutine about ten times what storing the body whole does), is stored as a **splice**: a blob `{"v":1,"parts":[…]}` whose parts, in order, are literal `text`, a raw `blob` or another `splice`, and whose expansion is the body byte for byte. The array's elements are stored by hash, in **groups**: an element over 4 KiB is a raw blob of its own, and a run of consecutive smaller ones is one raw blob of their bytes, a group that closes once it holds 4 KiB at an element whose sha256 has its low bit clear, or at 16 KiB whatever the hashes say. Where a group ends depends only on the elements since it began and the one after it (an element over 4 KiB closes the group before it), so a history that grows at its end keeps every group but its last, and one trimmed or edited earlier falls back into the same groups a few elements past the change. The groups are chained, each link a splice naming the link before it, the separator and the group's blob, so a request whose history continues an earlier one reuses that chain up to its last group; top-level members over 4 KiB outside the conversation (the system prompt, the tool list) are raw blobs, stored once. What "stored once by hash" holds to, then: an element over 4 KiB is on disk once per run wherever and however often it recurs; a smaller one is on disk once per distinct group that holds it — once for a stretch of history that is not edited, and again while it sits in the last group of a history still growing, which is stored again until it closes, or in a group beside an edit, a trim or a reorder. Measured (`internal/ledger/messages_test.go`), in apparent file sizes over fixtures whose elements are about 1.4 to 2.1 KB: a 60-turn conversation stored in 2.4 to 2.7 times its last request's bytes, where whole bodies take 33 and a per-element chain (one file per element, the first design) took 1.8; a 20-message window moved over 100 requests stored 5.6 times its distinct messages' bytes, where whole bodies take 17 and that per-element chain took 18. Those figures are not general. On disk every file is at least one block, and a history trimmed at its front rewrites a link file for every group on every request: the same window takes 823 files and 4,005,888 bytes of 4 KiB blocks, against 100 files and 3,276,800 bytes for whole bodies, about 22% more than storing whole bodies on a 4 KiB-block filesystem. For a growing conversation the open last group, up to 16 KiB, is stored again on every request, so the factor over the last request is roughly 1 + G/(2t) for groups of G bytes and turns of t bytes, and it rises as messages shrink: over 200 turns, about 17 times the last request in apparent bytes at 100-byte messages (83 in blocks), 8.5 at 300 bytes, 3.5 at 1 KB and 2.2 at 3 KB — still a small fraction of whole bodies, which take about 100 times the last request over 200 turns at every size. A spliced body has no `blob`, which in v1 names the file holding a body whole, and no file does: the payload carries `body_sha256` (the whole body's sha256), `frame` (the splice that rebuilds it) and `messages` (the chain's last link), and `Reader.Body` rebuilds the body and checks it against `body_sha256`, refusing (`ErrCorruptBlob`) a splice with no parts, one that contains itself, names a missing blob, costs more than a body of the recorded `size` is stored in, or rebuilds other bytes. The cost is bounded three ways, so the work is linear in `size` whatever the blobs directory holds (E16): files opened, splices and blobs together, at most 5·size/4 KiB + 8 (R15's bound on the files a body is stored in, plus its large members and slack); bytes of splice files read, all of them together, at most 3·size + 256 per file allowed + 64 KiB (text escaped as JSON is at most twice the text, and a part naming a file costs a few hundred bytes); and parts visited, at most two per byte. Bounding the parts visited alone is not enough: each splice read could be 2·size + 64 KiB, and a fan-out of splices padded with whitespace to that size, each naming one empty blob, would read size × 2·size bytes (12.6 GB and 15 s for a 64 KiB body). A reader that predates the three fields sees a body that was not stored, never a `blob` naming a file that is not there. Any other body — not JSON, no conversation member or two of them, a capture cut short — is stored whole as before, and a ledger written before splicing reads through the same call: `blob` names the body's file. That file is read only to the event's `size` and one byte more, and a longer one is refused (`ErrCorruptBlob`), so a tamperer who replaces a body's blob with a file of any size (E16) cannot make a reader allocate all of it (`FuzzBody`); the bytes read are also hashed against the blob's name, and a file that does not match is `ErrCorruptBlob` as a frame body that misses `body_sha256` is. No writer stores more under `blob` than the `size` it records (the uprobe path records the bytes it stores, the forwarder the bytes it read or the length the client declared, whichever is larger). An event that records no `size` is held to 1 GiB instead, the bound a splice without one already had, and every `ssl_response` is such an event, since its payload has no size field: a response blob can still cost a reader up to 1 GiB where capture's default caps keep at most 64 MiB of a body. A recorded `size` above 1 GiB is held to 1 GiB as well, for a splice and a blob alike, so a `size` tightens the bound and never loosens it: the forwarder's `size` includes the length the client declared, and net/http accepts a `Content-Length` up to 2^63-1, so the agent can put nearly any `size` on an honest event, and taken as it was a `size` of 2^63-1 would make `Reader.Body` return an empty body for a body stored whole, and one near it refuse an honest splice. No writer stores more than its capture cap of a body (8 MiB for the forwarder, 64 MiB for the uprobe path), so the ceiling refuses nothing a writer made; what it does not do is hold a sized event to less than 1 GiB when the agent declared more, so a tamperer's blob for such an event (E16) costs up to 1 GiB, as for an event without a `size`; tightening that needs an optional field beside `size` giving the bytes stored under `blob`, since `size` keeps the meaning v1 froze. Tightening the `ssl_response` bound needs an optional `size` on `ssl_response`, added under docs/VERSIONING.md's additive rule and written by both capture paths, that is at least the bytes stored under `blob`, as the invariant above requires: the decoded body's length when capture stored the body decoded (capture-derive.md R15: the blob holds decoded content and `content_encoding` names what the wire used), never the length on the wire, or `Reader.Body` would refuse every honest compressed response. A bound taken from the capture caps instead would refuse a ledger written with a larger cap. *Not covered: a conversation in any other member, which is stored whole until its provider's request shape is added to the three above, and a body the uprobe path captures, which it stores whole under `blob` itself, ahead of this stage, until it hands bodies to this stage the way the forwarder does.*

**R12 — `record` mode gates body storage, never event storage.** `off` → `run_start`, `run_end` and refusals reach `Append`: the supervisor and the kernel recorder (`TEGO_RECORD_OFF`) drop the advisory record-only events and keep every refusal (a filter upstream, not ledger-level; `internal/runtime/runstart.go`, supervisor `events.go` `recording()`), so no event a run's refusals produced is lost by turning the record off. `summary` (default) → every event appended but `ssl_request`/`ssl_response` bodies never captured, so R10 never fires; reads aggregated (E1). `full` → bodies flow through, R10 applies.

**R13 — `run_end.head` vs the chain anchor's head.** The payload's own `head` field is only for a P1 nested child's parent-head report — `omitempty`, absent in P0. The `head` written to `~/.tego/chain.log` is always this run's own final event id, written by `Close`.

**R14 — Blob collision is accepted, not verified.** On `EEXIST` at the rename target, `Blob`/`BlobFrom` treat it as dedup success without re-reading to confirm it hashes to `sha`. I8 holds for content this `Writer` wrote, but is *asserted, not enforced,* against a target corrupted by something outside this component (E28); a verifying read is left to §11 (a full read on every collision would defeat the point of skipping the write on a `Has` hit).

**R15 — No per-run blob-count ceiling.** The names `Close` fsyncs are bounded: past 4096 blobs written since `Open` the store keeps no more names and `Close` makes all of them durable with one `syncfs(2)` of the blobs' filesystem instead, so a run's memory and its `Close` no longer grow with its blob count. R10 bounds one field's inline size; nothing bounds how many oversized fields (and `blobs/<sha>` files) a run can produce — many unique near-4KiB fields can exhaust `blobs/` inodes before any token/cost budget reacts (those meter model traffic only). R11's splices bound what one request body can add, since the agent writes that body and it is recorded whether or not the upstream accepts it: a body of n bytes adds at most 4n/4 KiB + 3 files, however many elements it has — a frame, and per group a blob and a link, where every group but the array's last and those an element over 4 KiB closes holds at least 4 KiB of the body, so the worst case is an element over 4 KiB after each tiny one, four files per 4 KiB. (A per-element chain, one file per element, would add 50,001 files and 204 MB of 4 KiB blocks for a 100 KB body of 50k elements.) A request that was one file is now several, each at least a filesystem block, and a history rebuilt at its front writes a link per group again every request. The run-wide count is left open (§11), not a P0 ceiling. The uprobe path stores no blob for a request R11's pipelining depth refused: no response will pair with it, its body is not decoded, and its `ssl_request` carries the size the wire did and no `blob`, so an agent that floods a connection with pipelined requests adds lines, not files; and one call into the reassembler decodes at most one `MaxBody` (64 MiB) of content between all the bodies it completes, so a few bytes of `br` cannot become a blob of 64 MiB per request in one chunk.

**R16 — `gc` prefers the run id's embedded time over `ts` for retention age.** Per R7, `gc`'s `age > keep` comparison reads the run id's `time36` (`RUN-IDENTITY.md`) when parseable, falling back to the last event's `ts` only otherwise. `time36` is minted from the same host clock `gc` runs on, so this removes R7's specific violation (a stored past `ts` vs `time.Now()`) without eliminating cross-host/post-reboot clock-step risk generally.

**R17 — The refusal reason reaches the agent by errno and the record; the harness hook is not built.**
A refused agent should learn why. Built: the errno (`EACCES` from Landlock, `EPERM` from the
supervisor and tier 2's hooks; Python's `PermissionError` either way), the `refused` line with its `reason` and
`rule` in `events.jsonl`, and `last-refusal.json` in the run directory, rewritten after refusals as an advisory
hint (§3). Not built: the reason file or socket the agent opts into and the harness hook payloads (Claude Code and
Agent SDK `PreToolUse`/`PostToolUse` answers) that FEATURES.md S4 and E41 specify, P1, whose place is
`internal/runtime/reason` (a placeholder package) and `internal/adapters`. Condition: until E41 ships, a harness
learns a reason only by reading the ledger or `last-refusal.json`. *Amended 2026-10-24 (ADR 0061):* the placeholder
is removed; the reason file's format and wording are `pkg/spec/reason`, and `last-refusal.json` is its v1 (§3), which
says which refusals are new; the hook payloads are still to build.

## 6. Edge cases

1. **`record: summary` with a watched path.** Reads under `fs.watch`/`deny_read` are individual events even in `summary` mode; aggregation applies to every other read (`SEMANTICS` §7).
2. **Read aggregation window boundary.** An aggregated `fs.count` covers reads since the *previous* `fs` event for the same `(exec_id, nearest rule)`; the window closes on a new exec or run end, flushing any in-flight aggregate as a final `fs` event before `run_end`.
3. **`Append` with a non-existent `Kind`.** Errors before any bytes are written; treated as a programmer error, logged, never silently dropping the kernel action it represents.
4. **Two events identical down to the nanosecond.** Still get distinct `id`s — `seq` differs and is hashed.
5. **Short write from `write(2)`.** `Append` retries on the unwritten remainder; a genuine short write with no error is `ErrShortWrite`, never silently accepted.
6. **`ENOSPC` mid-`write(2)`.** May leave a torn line with no crash; `Reader.Iter` handles it exactly like a crash-torn last line — it cannot and need not distinguish the two. The Writer cuts the partial bytes back to the last whole line at once (it holds the lock and the file is `O_APPEND`, so everything past its last whole line is this line's), so the next line, a gap or `run_end`, starts on a line boundary. Only when that `ftruncate` fails is the Writer torn for the rest of the run (`ErrTorn`), so a run can write its `run_end` once the disk has room again.
7. **`ENOSPC` on the *next* `Append`.** The prior line stays intact; only the new one is torn/missing — fatal to the run (§7).
8. **Process OOM-killed mid-run (not a kernel crash).** Already-`write(2)`'d bytes survive in the page cache; only a torn *in-flight* write at the moment of death produces a partial last line.
9. **Wall clock stepped backward mid-run (NTP).** `ts` may be non-monotonic across consecutive `seq`; sorting by `ts` would misorder events, forbidden by R7. `mono_ns` stays correct for that run/boot.
10. **Wall clock stepped backward across a reboot between runs.** Two runs' `ts` ranges may overlap/invert; cross-run ordering uses the run id's `time36`, never `ts`.
11. **A 32 MB `ssl_request` body.** `BlobFrom` streams it (bounded memory); no upper bound enforced in P0 (R15, §11); still counts toward `tokens`/`cost_usd` budgets.
12. **Many small payload fields, each under 4 KiB.** A pathological `argv` still yields one long line, one `write(2)`. A line is bounded at `MaxLineBytes` (2 MiB), on both sides. A reader refuses a longer line as corruption (`ErrCorruptLedger`, naming the line), and `State`'s backwards search for the last line gives up past the same bound, instead of reading the line whole: `events.jsonl` is bytes a tamperer can write (E16), and a 64 MiB line would cost `Verify` and `State` several times its size in heap. The Writer refuses (`ErrInvalidEvent`) a line it would write at or past the bound before any byte reaches the file, so no reader ever meets one it wrote; R10's split keeps every real line far below it. Every reader's open (`events.jsonl`, the lock probe, a blob) is `O_NONBLOCK|O_NOFOLLOW` and refuses anything but a regular file, as the Writer's are, so a FIFO planted as `lock` or `events.jsonl` cannot hold `gc`, `status` or a sweep in `open(2)`.
13. **Concurrent readers while the writer appends.** `Iter()` at EOF on a line boundary yields cleanly, no torn line; a later fresh `Iter()` sees the new lines.
14. **A reader opens before `run_start` is written.** `open(2)` succeeds on the 0-byte file; `Iter()` yields nothing, no error.
15. **`flock` held by a `SIGSTOP`ped process.** Lock stays held indefinitely; `RunState` reports `running` forever — indistinguishable from alive-but-slow by design (`docs/ARCHITECTURE.md` §6).
16. **A blob file truncated/corrupted externally.** `Reader.Blob` does not re-verify on every `Get` (would defeat streaming); integrity-needing callers hash what they read themselves. `Reader.Body` bounds what it reads by the event's `size`, held to 1 GiB (and 1 GiB for an event that records none), whatever the files hold, a spliced body and a body stored whole alike, and refuses a file or a rebuild past it with `ErrCorruptBlob` (R11).
17. **A relative or symlinked `ledger_root`.** `Open` resolves `dir` as given; no extra symlink defense — the directory is trusted machine-config-derived input, not agent-controlled.
18. **Non-UTF8 bytes in `argv`/a path/a header value.** `path`/`argv` fields MUST be UTF-8-sanitized (invalid sequences replaced, raw bytes' sha256 optionally blobbed) rather than corrupting the line or failing `Append`. Replacement is one U+FFFD per invalid *byte*, by one sanitizer for every string on the line (a common field, an `attribution` field, a payload key, a payload value), and it writes the replacement *character*, not `encoding/json`'s `\ufffd` escape: `Decode` hands back the U+FFFD rune, so the escape would make re-serializing a decoded line produce different bytes and a different `id`, breaking I9 on any line holding an invalid byte. A payload *key* is sanitized before it is deduplicated and sorted, never after — two keys differing only in invalid bytes are one key once written, so they are one duplicate key and the event is rejected (`ErrInvalidEvent`) at encode time. This is the one case where E18 refuses rather than replaces, and it is the fail-closed side: writing both keys yields a line with a valid `id` that `VerifyLine` accepts but `Decode` rejects as malformed, which stops `Reader.Iter` at that line for the rest of the run and permanently fails `Writer.resume` on that directory.
19. **PID reuse between two events.** `pid`/`tid` alone are not a stable identity; every action event uses `exec_id` (`<run>/<pid>/<start-boot-ns>`), unique even across reuse.
20. **`cgroup` id is 0 or absent.** Recorded as `0`; downstream treats it as "unknown," never a valid zero id.
21. **`gc` concurrent with `tego status` reading the same run.** Deletion only after `RunState != running` and age exceeds retention; an fd opened before deletion keeps reading (unlink-while-open); a fresh `Open` after gets `os.ErrNotExist`.
22. **`gc` crashes mid-`RemoveAll`.** Partial deletion possible; the next `gc` re-attempts; a directory missing `events.jsonl` is treated as already-gone-enough; no surviving run affected. A directory whose `events.jsonl` cannot be *read* (mode in a shared `ledger_root`, `EIO`) is treated the same way — reported, never swept, still subject to retention — because the alternative is a directory no `gc` pass can ever clear.
23. **Machine upgrade mid-run** (binary replaced while live). The live `Writer`'s code path is unaffected; only a MINOR/MAJOR record-schema bump changes `MarshalLine`'s behavior.
24. **Two runs at the same nanosecond, same host.** Ids differ by `rand6`; a true collision surfaces as `ErrRunLocked` on the second `Open` (`run` exits 125).
25. **A payload field collides with a common-field name** (e.g. a hypothetical payload `seq`). `MarshalLine`'s splice rejects it at encode time (`ErrPayloadFieldCollision`) via a reserved-word check against R1.
26. **`Blob`/`BlobFrom` after `Close`.** Returns `ErrClosed`; never writes to an ended run's directory.
27. **A run directory with no `lock` file** (fixture, or a tool bypassing `Open`). Treated as "free," so `gc`'s sweep can still operate rather than erroring.
28. **`chain.log`'s own last line is torn.** Written by every run process over the host's lifetime, so a torn last line is arguably *more* likely over time than in any one run's own log. `ChainAnchor.Head`'s scan applies the same torn-last-line tolerance as `Reader.Iter`: a trailing line without `\n` is skipped, not an error; a torn line elsewhere is a hard read error. No run's own durability depends on `chain.log` being intact — only chain verification (`tego events --verify`) does.
29. **`file.Sync()` succeeds but `ChainAnchor.Append` then fails** (e.g. `chain.log`'s directory full, or a permissions problem specific to that shared file). The run is fully durable and `StateEnded` (which only inspects `run_start`/`run_end`/`lock`) with a real terminal `id`, yet `chain.log` has no anchor line — I3's "unbroken hash chain" becomes silently unverifiable by anything trusting `chain.log` as root of trust. `Close` returns `ErrAnchorWrite` distinctly (§4) so this can be detected/logged, and `tego events --verify` reports the run as `ErrAnchorMissing` (exit 1) from then on. The one exception is the live-index sweep (§3 Live index): for an ended run the index still lists it rebuilds the line under the run's lock, after the chain verifies. A run whose `Close` failed the anchor write is cleared from the index, and nothing rebuilds its line, deliberately: an anchor written from the ledger it is meant to vouch for attests nothing — whoever could truncate the ledger could then have it re-anchored at the truncated head. *Settled 2026-09-22; this case used to wait for a future `gc --verify`/`doctor` reconciliation pass (§11).*
30. **`gc`'s retention math across an NTP step.** Per R7/R16, comparing a stored `ts` to `time.Now()` risks `gc` keeping every run forever (backward step) or deleting a fresh run early (forward-then-corrected jump). R16's `time36`-first rule mitigates the common case but not a clock step *between* run-id minting and the `gc` sweep — that residual window is unresolved (§11).

## 8. Invariants

**I1 — Append-only for every complete line.** Every writing open of `events.jsonl` in `internal/ledger` carries `O_APPEND` (`openFiles`, from `Open`, is the only one), and no path seeks backward, so a line once complete is never moved or rewritten. The file is truncated in exactly two places, both under the run's exclusive lock and both removing only bytes that never formed a complete line: `resume` discards an unterminated tail that does not decode (a writer that died mid-`write(2)`), then records the loss as a `torn-tail` gap; and `cutTornLine` cuts a partial line a failed `Append` left back to the last whole line (E5). Enforced by: `TestEventsFileOpensAppend`, which parses the package's sources and fails on any writing open of `events.jsonl` without `O_APPEND`, and on any `os.Create`/`os.WriteFile` of it; `TestResumeAfterTornTail` and `TestResumeLineMissingOnlyItsTerminator` for the truncation.

**I2 — Every production write path redacts before persisting, but `Append` itself does not enforce this.** `run.go`'s pipeline wiring always composes `w.RedactStage` ahead of `w.Append` — that composition is what keeps a credential off disk, not a guarantee `Append` provides alone (see R9). Enforced by: (a) a unit test on `RedactStage` directly, asserting no `authorization`/`x-api-key` value survives, both `source` legs; (b) a wiring test asserting `run.go`'s composed pipeline includes `RedactStage` before the ledger sink; (c) review flags any `w.Append` call outside that pipeline in production code.

**I3 — `id`/`prev` form an unbroken hash chain within a run.** `event[i].Prev == event[i-1].ID` for `i>0`; `event[0].Prev == ""`. Enforced by: `Reader.Verify` (§4) in fixture tests and in `tego events <run> --verify`. Per E29, this is about one run's own file, independent of whether `chain.log` has its anchor line.

**I4 — `seq` is gapless and strictly increasing.** `event[i].Seq == i`. Enforced by: `w.seq++` under `w.mu`; a reader finding a gap raises `ErrCorruptChain`, distinct from a torn last line.

**I5 — One `write(2)` per `Append`.** No line is assembled via multiple partial writes. Enforced by: the full buffer built before one `Write` call; the short-write retry (E5) targets the same line's unwritten suffix only.

**I6 — A run's `events.jsonl` byte-for-byte matches every past `Append`/`Close`.** No in-place edit, ever. Enforced by: I1, plus `gc` only deleting whole directories, never opening a surviving run's file for writing.

**I7 — `RunState` is derivable from the filesystem alone, no global registry.** `List`/`State` reconstruct everything from directory entries, `run_start`/`run_end` presence, and the `lock` file's `flock` state. Enforced by: `RunRepository` holds no persistent cache beyond one call's result. The live index (§3) names which runs `run` and `stop` sweep, not what state any run is in: a sweep still reads each listed run's state from its ledger and lock, an entry of an ended run is only cleared, and `gc` never reads the index, so a deleted or damaged index costs a full pass, never a wrong state.

**I8 — Blob content-addressing is exact for content this `Writer` wrote.** `blobs/<sha256>` hashes to `<sha256>` for every blob this write path produced — the filename is never chosen independently of the computed hash. **Not** enforced against a pre-existing, externally-corrupted target (R14/E28 state that gap explicitly).

**I9 — `Decode(MarshalLine(e))` round-trips for every valid `e`** (modulo R2's double-serialization — decoding the *final* bytes reproduces every field except `Payload`, which returns spliced-and-resorted, not necessarily byte-identical for non-canonical input key order — expected, tested explicitly).

**I10 — Every exported error is a sentinel `var Err…`, wrapped with `%w` at each layer** (`docs/REPO-LAYOUT.md`), so `errors.Is(err, ledger.ErrRunLocked)` works through the CLI's own wrapping.

**Changes.**
- 2026-09-24, I7: the live index names what to sweep, never a run's state.
- 2026-09-25, I1: states the two tail truncations; an AST test enforces `O_APPEND`.

## 9. Conventions and best practices

- **Naming**: neither package stutters (`record.Event`, `ledger.Writer`); no `util`/`common`/`helpers`. Codec in `record/line.go`; writer in `ledger/writer.go`; reader in `ledger/reader.go`; gc in `ledger/gc.go`; the pipeline `Stage`s in `ledger/redact.go` and `ledger/blob.go` (same files own the underlying `Blob`/`BlobFrom` methods); repositories in `ledger/repository.go`.
- **Errors**: every §7 failure mode has a sentinel (`ErrRunLocked`, `ErrShortWrite`, `ErrClosed`, `ErrAlreadyClosed`, `ErrUnsupportedVersion`, `ErrCorruptChain`, `ErrPayloadFieldCollision`, `ErrAnchorWrite`, and for `Verify` `ErrUnverified` and `ErrAnchorMissing`), wrapped with `%w` at each layer; `record.Reason` values are never used as Go `error` values.
- **Logging**: never to stdout/stderr directly; operational detail goes through an injected logger interface to `~/.tego/tego.log` (`docs/OPERATIONS.md`).
- **Context**: `Append`/`Blob`/`Close` take no `context.Context` (nothing to cancel); `RunRepository`/`gc` do, so a large `gc --keep 0` sweep is interruptible.
- **Goroutine ownership**: `Writer` is not safe for uncoordinated concurrent goroutines — the product drains one pipeline channel into `Append` (`docs/P0-DESIGN.md` §2.4); `w.mu` is a safety net (I4/I5), not an invitation.
- **Resource lifetimes**: `Writer` owns two `*os.File`s and two directory descriptors (the run directory and `blobs/`, §3), closed only by `Close`; `Reader` owns one, closed by a caller-deferred `Close`. No finalizers.
- **Fuzzing**: `record.Decode` is a fuzz target — arbitrary bytes never panic, malformed input always errors.
- **Benchmarks**: `BenchmarkAppend` (<20 µs, no fsync, `docs/P0-DESIGN.md` §9) and `BenchmarkIterFullRun`, run in CI on every PR touching the package.
- **Doc comments**: every exported identifier's comment starts with its name; `Event`'s states the canonical field order (R1).

## 11. Open questions

- **§5 R2's zero-placeholder hashing convention.** The normative docs establish `id = sha256(line as written)` and "the bytes hashed are the bytes written" but don't spell out a self-referential hash's mechanics; this document commits to hash-with-`id`-zeroed-then-splice so implementation is unblocked.
- **`record.Reason`'s three added codes amend a stated closed set without documentation.** `path-unresolved`, `ask-unreadable`, `ask-unavailable` are each independently normative (`SEMANTICS.md` §§2/6, `ARCHITECTURE.md` §§7/9) but `spec/reason/REASON-CHANNEL.md` frames its 16 codes as *the* closed set and lists none of them; the channel now lists them.
- **`RunRepository`/`BlobRepository`/`ChainAnchor` as named Go interfaces.** No normative doc names these three; synthesized from `docs/P0-DESIGN.md` §2.10 plus `docs/REPO-LAYOUT.md`'s repository mapping.
- **Maximum request/blob size, and per-run blob count (R15).** No ceiling exists in the normative docs for a single body or a run's blob count; 32 MB (E11) is illustrative. Whether P0 should add one (with a `gap` on truncation) is unresolved.
- **`ledger_root` on a non-local filesystem (NFS).** R4's atomicity argument is Linux-local-filesystem-specific; no doc forbids a network path. Whether `doctor`/`compile` should warn is unresolved.
- ~~**A `gc --verify`/chain-verification flag, and reconciling a missing `chain.log` anchor (E29).**~~ **Settled 2026-09-22:** the command is `tego events <run> --verify` (§4 `Verify`, `limits-check-doctor-cli.md` R29), and a missing anchor is reported, never rebuilt (E29).
- ~~**`Reader` follow/tail mode.**~~ **Settled 2026-10-24:** the follower is `internal/ledger`'s (`Follow`, `WatchLive`, §4), inotify with a 1 s poll backstop; `internal/check/events` renders what it yields and `tego events --follow` prints it (`limits-check-doctor-cli.md` R29).
- ~~**`RefusedPayload` vs `last-refusal.json`.**~~ **Settled 2026-09-24:** the ledger `Writer` owns the file: `Append` hands each refused line to it, and it is written off `Append`'s path, latest wins, at most every 10 ms and once more at `Close`/`Abandon` (§3).

### Append batches (amended 2026-11-03, M5)

`Writer.AppendBatch(events ...*record.Event) error` accepts already redacted and
blob-split events and appends them in order while holding the writer mutex once.
The runtime pipeline and DNS broker use it for a refused action followed by its
mirror, after preparing both payloads. Every event still has its own sequence,
hash and single write; other writers cannot insert lines between the pair.
This is serialization, not transactional durability: an error can leave a written
prefix, and requires the same run termination as an `Append` failure. No event
format changes. Readers retain the legacy four-line pairing fallback for existing
ledgers; they cannot reliably repair historically displaced mirrors.
