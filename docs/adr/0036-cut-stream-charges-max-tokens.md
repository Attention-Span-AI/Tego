# ADR 0036: a stream cut before its final message_delta is charged max_tokens

Status: accepted 2026-09-24; implemented in internal/runtime/derive/anthropic (parser.go, stream.go), pkg/spec/record (Usage.OutputBound) and internal/runtime/capture/forwarder (usage.go, listener.go). Amends capture-derive.md R29 and limits-check-doctor-cli.md R1.

Decision: (1) An Anthropic Messages API event stream that ends without a `message_delta` carrying usage (the client left, the upstream closed, a cap or an error event cut it) is charged the request's `max_tokens` as its output tokens, or the output it reported if that is larger. The usage is written with `output_bound: true`, an optional field of `usage` within record v1, so the ledger says the output count is a bound and not the model's report. (2) When the request's `max_tokens` is not known (the request body was not captured, did not parse, or carried none), there is no bound, and the exchange is unmetered (`derive.Facts.Unmetered`): a run with a token or cost budget ends there (R1). (3) On the forwarder, a `message_delta` its wire scanner read replaces the bound with the reported count. A scanner that saw only `message_start` does not clear derive's unmetered verdict.

Why: [documented, code: internal/runtime/derive/anthropic/types.go merge] `message_start` carries the input and cache counts with a placeholder output count; the output count arrives only in the final `message_delta`. [documented, R1 before this ADR] A stream cut after `message_start` was counted with its input tokens alone and called an accepted shortfall. [inference] The model generates, and the provider bills, output up to the point the stream stopped, which can be as much as `max_tokens`; an agent could reach a token or cost ceiling several times over with streams it interrupts before the end. `max_tokens` is a deterministic upper bound the request itself states, so charging it never undercounts, and needs no estimate from the bytes seen.

Options considered:
- Keep the input-only count (the previous accepted shortfall): the budget undercounts by as much as `max_tokens` per interrupted call, without limit across calls. Rejected.
- End the run (treat every cut stream as unmetered): rejected. A user interrupting a stream (Esc in a coding agent, a client cancelling a turn it no longer needs) is normal, frequent operation; ending every budgeted run at the first interrupt would make budgets unusable. Unmetered is kept only for the case with no bound at all.
- Estimate output from the content deltas seen (text length, a tokenizer): approximate, provider-specific, and a model-side judgment Tego does not make (ADR 0003); it can also undercount, since generation continues past what reached the client.

Consequence: Interrupted streams overcharge: a budget can trip earlier than true spend would. The ledger marks each such charge (`output_bound`), so a report can say how much of a total is a bound. An agent that sets a huge `max_tokens` and interrupts is charged that amount, which is its own choice. The chat-completions endpoint is unchanged: a stream there that carried no usage chunk is already unmetered.

*Amended 2026-09-24:* (2)'s "the request body was not captured, did not parse" no longer covers a body capture kept only as a prefix: its top-level `max_tokens` is read off every byte of the body as it is relayed (forwarder) or reassembled (uprobe path), by exact-case key with any case-variant or duplicate key leaving no bound (internal/runtime/capture/maxtokens), and bounds the stream. (3) also applies when derive's whole copy stopped short of a `message_delta` the scanner read (derive stops at a line it cannot parse): the wire's count replaces the bound. A request that got no response bytes at all is not a cut stream: it is unmetered by ADR 0037, which states the distinction.

*Amended 2026-09-24:* derive reads a whole request's `max_tokens` by the same rule as that scanner, and with the same code (`anthropic.MaxTokensScanner`, which capture/maxtokens now wraps): `encoding/json` folds key case, so `{"max_tokens":64000,…,"MAX_TOKENS":1}` was bounded by 1 on derive's own reading. A body that names `max_tokens` more than once in any spelling, or only in another spelling, has no `max_tokens`, and (2) applies: the exchange is unmetered. A stream that fails after `message_start` is still read to its end for a `message_delta`'s usage, which replaces the bound as in (3). A stream whose first event is an `error` (before any `message_start`) began no message: it is an error answer, charged nothing and not bounded. An `error` event after `message_start` keeps the bound.

*Amended 2026-09-24:* the `capture/maxtokens` package named above was removed; the one
streaming `max_tokens` scanner is `anthropic.MaxTokensScanner` in derive/anthropic, and httpstream reaches it through
`Options.BodyScanner`, which capture wires. The rule is unchanged.

Note 2026-09-30: (1) charges nothing to a stream whose request declares a server-side tool (a tools[] entry whose type is not custom). The tool's per-request counts, and the input its loop grew, are reported only in the final message_delta that the cut lost, so max_tokens as output is not an upper bound there; the exchange is unmetered, as with no bound at all (options above). The scanner (anthropic.MaxTokensScanner) reads the tools array as far as each entry's type and fails closed on a spelling it cannot follow.

Note 2026-09-30: a `message_delta` whose usage carries no `output_tokens` is not the final usage: it holds no output count, so a stream cut after it is still bounded by (1) (parser and scanner both). A top-level `mcp_servers` key, in any case or repeated, marks a server tool like a `tools[]` entry, since the MCP connector's loop runs server-side.
