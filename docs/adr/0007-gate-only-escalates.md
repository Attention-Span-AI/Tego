# ADR 0007: lists decide in the kernel; the gate only escalates

Status: accepted 2026-09-21.
Amended by ADR 0041 (accepted 2026-10-05: where a gate verdict is completed, as (A) race-free, (R) refused or (D) disclosed best effort, per rule, action and tier).
Amended in part by ADR 0048 (accepted 2026-10-06): the gate's `exec matches` also reads its pattern with the shared command matcher (the union of both readings); the gate still only escalates.
Amended in part by ADR 0044 (accepted 2026-10-16, not built): an exec scored into the gate's ask range is held, asked and completed through the trace-gate at every tier, instead of the unsupported-completion refusal.
Decision: allow/ask/deny lists compile to kernel (or Landlock) decisions. Gate rules run in the supervisor on actions that reach it and may raise allow→ask or ask→refused by score; they never lower a verdict. Predicates are a closed enum.
Why: two mechanisms for one decision need one precedence rule, and "the kernel is the floor" is the only one that keeps the security property while keeping a scored gate.
Consequence: `compile` prints the effective decision per declared entry and flags contradictions; argv predicates depend on the seccomp `execve` notification.

Implementation (2026-10-04): bounded enum/integer evaluation and supervisor escalation are built; agent-contract R22a records thresholds, scopes, copied-fact provenance and supported safe completions. Exec scores in the ask range fail closed with an explicit unsupported completion. Safe kernel-exact exec approval remains open; the gate is not a race-free final argv claim.

Implementation note (2026-10-20): the thresholds now read "below 50 allow; 50 to 80 ask; above 80" refused: a score below `allow` allows, `allow` to `ask` (both inclusive) asks, above `ask` refuses. A score of exactly `allow` was allowed before; it now asks, the more conservative reading. `allow` must be at least 1 (`1 <= allow < ask <= 100`), so an unmatched action, score 0, is always allowed; `allow: 0` is refused at compile instead of silently meaning "ask everything". `MayAsk`/`MayEscalate` count from `allow`, so the compile warnings, the broker requirement and held completion agree with `Evaluate` at the boundary.
Scores sum: Tego keeps the saturating sum of every matching rule's score, not the highest rule an action matches. Options weighed: (1) highest rule; (2) saturating sum, as built; (3) a per-contract choice between them. Chosen: (2). With scores 0..100 the sum is never below the highest, so (2) never allows what (1) would ask or refuse, while (1) allows an action several rules each score below `allow` (30 + 20 asks under (2), allows under (1)); security breaks the tie. (3) was rejected: a second meaning for the same numbers doubles what a reader of a contract must know, and the permissive choice would be a switch away. Tests `TestGateThresholdBoundaries`, `TestGateScoresSumNotHighest` and `TestCompileTestGateBoundariesAndSum`.

Implementation note (2026-10-20): the sum crosses the fs kinds of one action. An action the gate scores by both fs kinds, an open that reads and writes (`O_RDWR`, or `O_RDONLY` with `O_CREAT` or `O_TRUNC`) and the end of a rename or hard link that leaves its name (the source, and the destination too under `RENAME_EXCHANGE`), had kept the stronger of the two kinds' sums: the highest-rule reading the note above rejects, between kinds. Under `fs.read matches "*.env": 30` and `fs.write outside worktree: 30` with the default thresholds, an `O_RDWR` open or a rename of `out/prod.env` scored 30 and was allowed. Such an end is now one action (`gate.Action.Reads`): every matching rule of either kind counts once (the kinds' rule sets are disjoint) and the scores sum, here 60, which asks. Options weighed: (1) sum both kinds of one end, chosen; (2) keep the stronger kind's verdict, rejected as the less conservative reading, so security breaks the tie. The two ends of a rename or hard link stayed two actions, the stronger end kept: they are two objects, and a sum across them would count `fs.write outside worktree` twice for one call (superseded by the next note). `MayAskReadWrite` and `MayEscalateReadWrite` are the subset-sums over both kinds' rules together, so the broker requirement, held completion (`openMayEscalate`, `NeedsOpenDeputy`) and the (D) cells of ADR 0041 D7 see a combination neither kind reaches alone. `compile --test`'s `fs.rename` row sums its source's kinds as a run does. Tests: `TestGateReadingWriteSumsBothKinds`, `TestGateSumsReadAndWriteKindsOfOneEnd`, `TestCompileTestGateSumsReadAndWriteOfAMoveSource`, and the cases added to `TestBestEffortCellsAreDisclosedAtCompile` and `TestGateConfigDefaultsEnableOnlySafeApprovalBroker`.

Implementation note (2026-10-20): a rename or hard link is one gate action over both its ends. The note above kept each end its own action and the stronger end, because adding the two ends' totals would count `fs.write outside worktree` twice for one call. That reason rules out summing the ends' totals, not counting each rule once when either end matches it; under the per-end split a read rule matching the source and a write rule matching the destination never added up, so under `fs.read matches "*.env": 45` and `fs.write outside worktree: 45` (thresholds 50/80) `rename(work/prod.env, out/moved)`, which moves a secret out of the worktree under a name the glob does not match, was allowed at 45 while `rename(out/prod.env, out/moved)` was refused at 90. Options weighed: (1) each end its own action, the stronger kept, as built; (2) both ends' totals summed, rejected because a rule matching both ends would count twice; (3) one action over both ends, every rule that matches an end it scores counted once (the write predicates on either end, the read ones on the source and, under `RENAME_EXCHANGE`, the destination), the scores summed. Chosen: (3). It never counts a rule twice, is never below (1)'s score, and differs from (1) only where different rules match different ends, and the more conservative reading wins, as the first note's sum does. The same flow made as two calls, a read of the source and a write of the destination, stays two actions each scored alone: one call is one action, and the gate scores what a call does. `gate.Action` carries the move's other end (`Dest`, `DestReads`); `gateFS` and `compile --test`'s `fs.rename` row (`EvaluateGateRow`) build one action; the supervisor's `stronger` is gone. `MayEscalateReadWrite`/`MayAskReadWrite` are unchanged, since a move's matching rules are still a subset of both fs kinds' rules. Tests: `TestGateMoveCountsEachRuleOnceAcrossItsEnds`, `TestGateSumsReadAndWriteKindsOfOneEnd` (a matching source renamed or linked out of the worktree is refused at 90), `TestCompileTestGateSumsReadAndWriteOfAMoveSource` (refused at 60, 30 before).

Implementation note (2026-10-20: the read pattern's model). The earlier fixes patched how a move's ends meet `fs.read matches`, and two faults with one cause remained: a read pattern was text handed to `filepath.Match` against a string derived from the path (the base name, the path from the worktree, or the path), so nothing tied what an author may write to the clean paths it is compared with, and every new question about it (the 2026-10-20 notes in ADR 0041: could a path beneath this directory match?) needed a second reader of `filepath.Match`'s grammar. One: `fs.read matches "./secrets/*"`, a doubled or trailing `/`, a `.` component and a pattern malformed after its first chunk (`filepath.Match(p, "")` stops reading at the first chunk that fails, so `a*[` passed) were accepted and never fired, with no warning, though `filepath.Rel` and the walk only ever produce clean paths. The other: the second reader, an automaton stepping a rune at a time, missed what `filepath.Match`'s byte-skipping star matches, so under `"*[^é/]/*"` the move of a directory named `é` scored 0 although `é/k` beneath it matched. The model now: a read pattern with no `/` outside a character class matches a base name; one with such a `/` is a path pattern, a sequence of component globs separated by `/`, each a `filepath.Match` pattern matching one name, absolute when it starts with `/` and otherwise matched against the path from the worktree. A path matches it when the two have as many components and each name matches its glob; a move's end lies above a match when it has fewer and each matches (`readPattern.above`). Both questions run `filepath.Match` itself on one name at a time, so they cannot read a glob differently, and no other reader of the grammar is left (the automaton is deleted). Compile accepts a read pattern only when the grammar accepts all of it (`parseGlob`, also for `exec matches`) and some clean path matches it: every component glob matches a name other than `""`, `.` and `..` (`witness`, confirmed by `filepath.Match`), except that a relative pattern's leading components may stand for the `..` of a path out of the worktree. So an empty, `.` or misplaced `..` component and a class that matches no name are refused, the refusal naming the spelling without the empty and `.` components when that one is accepted (`write "secrets/*"`). Two constructs are refused because the component reading would read them otherwise than `filepath.Match` reads the whole string: an escaped `/`, and in a path pattern a class that can match `/` (`filepath.Match` lets `[^x]` match the separator, where `*` and `?` cannot). With those refused, each `/` of a path is matched by a `/` of the pattern, so the component reading answers as `filepath.Match` on the whole string for every pattern compile accepts (the root `/` excepted until the next note) (`TestReadPatternAgreesWithFilepathMatch`, multibyte names and a byte that is no UTF-8 included). A `/` inside a class no longer makes a pattern a path pattern: `"[^/]*.env"` now matches a base name anywhere, where it matched only the worktree's top level, the broader reading. `~/` expands against the home cleaned of a trailing `/`. Options weighed: (1) clean the pattern silently, rejected: `filepath.Clean` is lexical and rewrites `a/*/../b` to `a/b`, changing what a glob means, and the effective policy would print a rule its author did not write, where an exec pattern's first word is refused with its fix (R2); (2) clean the matched string instead (prefix `./`, keep doubled separators), rejected: it fits one spelling and leaves the rest; (3) keep the automaton and make it step bytes as the star does, rejected: a second reader stays a second reader, and the next corner of the grammar diverges again; (4) read a class as never matching `/` (POSIX `FNM_PATHNAME`), rejected: it silently narrows what an accepted contract matched, the less conservative reading; (5) match whole strings with `filepath.Match` and components only for a move's ends, rejected: two code paths whose agreement would rest on a test alone. A relative pattern with more leading `..` components than the worktree has names matches nothing at run; the worktree is the run's, so compile does not refuse it (a reason that does not hold: compile captures the run's worktree, and refuses such a pattern since the second 2026-10-24 note). Tests: `TestGateReadPatternMatchesSomeCleanPath`, `TestGateMovedDirectoryWithAMultibyteName`, `TestReadPatternAgreesWithFilepathMatch`, `TestReadPatternHasAWitnessAndTheGrammarIsReadWhole`, `TestGateConfigRefusesAReadPatternNoCleanPathMatches`, `TestCompileRefusesAReadPatternNoCleanPathMatches`.

Implementation note (2026-10-20): the root. The component reading skipped every empty name, so the root `/`, the one clean path whose last name is empty, had no components and matched only the pattern `/`, where `filepath.Match("/*", "/")` is true: under `fs.read matches "/*": 90` at tier landlock, `ls /` was allowed at score 0 while `ls /etc` was refused, a narrowing of what an accepted contract matched that the note above rejects as option (4). `readPattern.match` now answers the root as `filepath.Match` does: an absolute pattern of one component matches `/` when that component matches the empty name (`/*`, as `/` itself did). No other clean path has an empty name, so the note above's claim now holds without exception; `TestReadPatternAgreesWithFilepathMatch` holds `/`, `/*`, `/?` and `/*/*`, and `TestGateReadPatternMatchesSomeCleanPath` scores a read of `/` under `/*`.

Implementation note (2026-10-24): what the refusals of an escaped `/` and of a class that can match `/` say. The refusal of an escaped `/` said it "never matches a path's separator", and R22a's 2026-10-20 Changes entry listed both constructs among patterns that "were accepted and never fired". Both are false: `filepath.Match("a\/x", "a/x")` and `filepath.Match("x/[^y]z", "x/az")` are true, and the gate before the component reading handed every pattern holding `/` to `filepath.Match` against the path, so they fired. They are refused for the reason the note above gives, the component reading would read them otherwise, which makes the refusal a compatibility break, recorded in the CHANGELOG. The escaped `/` refusal now says that `filepath.Match` matches it across a separator and names the pattern with each escaped `/` outside a class written as `/` when that pattern is accepted (`write "a/x"`; `plainSlash`); a pattern whose only `/` is inside a class is a base-name pattern, and its refusal says a base name never holds `/` and where a path pattern's `/` goes. Rejected: accept an escaped `/` as a separator, the reading `filepath.Match` gives it, since that is a second spelling of one pattern that the effective policy would print as its author did not write it, the reason (1) above rejects. Tests: `TestGateReadPatternRefusalSaysWhatFilepathMatchDid` checks each case against `filepath.Match` first, so a case that never fired cannot stand in for one that did.

Implementation note (2026-10-24): a relative read pattern beyond the worktree's ancestors. The fourth 2026-10-20 note accepted a relative pattern with more leading `..` components than the worktree has names because "the worktree is the run's, so compile does not refuse it". The reason does not hold: the compile that builds the run's RuleTable captures that worktree (`RuleTable.Workdir`, the resolved compile working directory, which the supervisor and `compile --test` score against), so it can tell the rule never fires there, and accepting it silently left a read the author meant to score unscored. Compile now refuses it (`Policy.CheckWorktree`, called where the worktree is captured; `gate.New` still cannot ask it). A path from a worktree with n names starts with at most n `..` components, and only there, so a pattern matches nothing from it when its leading components must match `..` more than n times: those up to the last one that matches `..` and no name (`readPattern.up`; a glob such as `*` matches names as well, so `*/x` is accepted under the root). When those components are each `..`, the refusal names the absolute pattern the agent's own path resolves to, the parent of the root being the root (worktree `/home/u`: `../../../secrets/*` is `write "/secrets/*"`). A worktree that is no absolute path is not checked; its reads are incomplete and unscored as before. Options weighed: (1) a warning, rejected: the author's rule protects nothing in this run, and the conservative reading refuses a boundary that cannot be enforced; (2) correct only this note's reason, rejected for the same cause; (3) clamp the pattern's `..` at the root as path resolution does, rejected: it is a second reading of the pattern that the effective policy would print as its author did not write it, the reason the fourth note's option (1) gives. The same contract compiled in a deeper worktree is accepted there, as its relative patterns are read from that worktree. Tests: `TestGateReadPatternReachesTheWorktreesAncestors`, `TestReadPatternBeyondAgreesWithAPathFromTheWorktree` (refused exactly when no path of k `..` and witness names, k up to the worktree's depth, matches), `TestCompileRefusesAReadPatternBeyondTheWorktreesAncestors`.
