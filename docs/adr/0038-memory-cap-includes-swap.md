# ADR 0038: a memory cap bounds swap too: memory.swap.max is 0 beside memory.max

Status: accepted 2026-09-24 (traceability audit of runtime-launch.md R10); implemented in internal/runtime/cgroup (limitFiles, SetLimits). Amends runtime-launch.md §4 `SetLimits`.

Decision: when a run's contract or machine config caps memory (`limits.memory`, so `memory.max` is written), `SetLimits` also writes `memory.swap.max` = `0` in the run's scope, right after `memory.max`. Where the kernel accounts no swap to cgroups the file does not exist and that write is skipped; nothing else changes. `memory_high` alone caps nothing and leaves swap alone. A contract has no key for swap.

Why: [measured, 2026-09-24] `memory.max` bounds the RAM a cgroup holds, not its memory: over the cap the kernel reclaims, and with swap on the host it writes the agent's anonymous pages out instead of OOM-killing it. `TestMainProcessOOMIsReasonOOM` (a 1 GiB allocation under `memory: 64MiB`) skipped in both CI jobs, whose runners have swap, as "memory.max not enforced?". In the KVM guest it passed with no swap and skipped once a 1.3 GiB swap device was on (`swapon` of a loop device); with this change it passes with the swap device on. So on any host with free swap, a 64 MiB agent could grow to the size of the swap space, and R10's `reason=oom` never came. [documented] `internal/runtime/cgroup`'s own `TestIntegrationOOM` already wrote `memory.swap.max` 0 by hand before setting `memory.max`, for this reason. [documented, external] Kubernetes' default for Linux containers is no swap (`memory.swap.max` 0 under cgroup v2, KEP-2400's `NoSwap`); Docker bounds memory plus swap at twice `--memory` unless told otherwise; systemd's `MemorySwapMax=` defaults to unlimited.

Options considered:
- Leave swap unbounded (systemd's default): the cap then means RAM, and an agent's memory is bounded only by the host's swap; the OOM reason depends on whether the host has swap. Rejected: a budget named `memory` that a host setting silently widens is the failure a limit exists to prevent.
- Twice the cap, as Docker does: bounded, but an agent over its cap is slowed by swapping before it is killed, and the number is not one an operator wrote. Rejected for P0; a contract key for swap can be added if an agent needs it.
- A contract key (`limits.swap`): no agent has asked for one; additive later without changing this default.

Consequence: an agent over its memory cap is OOM-killed on every host, with or without swap, and `run_end` says `oom` (R10). An agent that relied on swapping under its cap now dies at the cap; its contract raises `memory`. A kernel booted without swap accounting (`cgroup_memory=noswap`, `swapaccount=0`) keeps the old behaviour, since it has no per-cgroup swap to cap.

Note, 2026-09-24: "keeps the old behaviour" was the bypass this ADR closes, reopened on those kernels without a word: with swap accounting off and a swap area on, the kernel still swaps the agent's pages out past `memory.max`, only unaccounted, and `SetLimits` skipped the missing `memory.swap.max` silently. There is no per-cgroup knob to write there, so the run cannot close it; it says so. When `memory.swap.max` is absent from the run's cgroup and `/proc/swaps` lists an active area, a run with a memory cap prints one warning (`[swap-uncapped]`, naming the areas and the fix) and records a gap `what=limits`, `why=memory-swap-uncapped` after `run_start` (`cgroup.UncappedSwap`, `runtime.checkSwapCap`); `tego doctor` reports the host as a failed check, D9 `swap`, whose fix is to enable swap accounting (remove `swapaccount=0` and `cgroup.memory=noswap` from the kernel command line) or turn swap off. The check gates no tier. Tests: `TestUncappedSwap` (a fake cgroup directory and a stubbed `/proc/swaps`), `TestMemoryCapIntoSwapIsALimitsGap`, `TestProbeSwap`.
