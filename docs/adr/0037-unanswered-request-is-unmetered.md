# ADR 0037: a model request that got no response bytes is unmetered, on both capture paths

Status: accepted 2026-09-24; implemented in internal/runtime/capture/forwarder (listener.go derive, dialFailed) and internal/runtime/capture/uprobe (events.go unanswered, emitResponse, emitRequest; uprobe.go closePending). Amends ADR 0035 (2) (now one rule for both paths). Distinct from ADR 0036, which it leaves as it is.

Decision: (1) A request to a model host, or to a host capture never learned, that got no byte of a response is reported unmetered (`runtime.ReportUnmetered`), which ends a run with a token or cost budget. "No byte of a response" means no status line: on the forwarder, the upstream round trip returned an error, or the run ended with the exchange in flight; on the uprobe path, the request was still waiting when its connection ended (closed, restarted, gapped, the source stopped), when a later response on the connection showed its answer would never come, or when the per-connection table of waiting requests gave it up. (2) One exemption, forwarder only: an upstream leg whose dial failed (`*net.OpError` with `Op == "dial"`) sent no byte, and is not reported. Every other failure, a TLS handshake's included, is not told apart and is reported. (3) Once any response byte has arrived, ADR 0036 applies: a stream interrupted after `message_start` is charged the request's `max_tokens` as a bound and the run goes on; only a stream with no known `max_tokens` is unmetered. So an interrupt before the first response byte ends a budgeted run, and an interrupt after `message_start` does not.

Why: [documented, code before this ADR] The two paths disagreed. The uprobe path's `closePending` reported a waiting request unmetered (ADR 0035 (2)); the forwarder, on a round-trip error, called `finish(x, nil)`, and derive's nil-response branch recorded one `gap why=malformed` and nothing else, so a budgeted run went on. [inference] The upstream reads the request before it answers: a connection it drops after reading the prompt, or a client that leaves while the model is generating the first token, may have been billed for the whole input and some output. Nothing on the wire says how much. A budget that is silently not enforced is the failure a budget exists to prevent, and one rule for both paths is the one that holds whichever captures the run.

Distinction from ADR 0036: ADR 0036 bounds an answer that has begun. Its `message_start` states the input and cache counts, and the request's `max_tokens` bounds the output, so the charge is an upper bound and the run can go on. Before any response byte there is no input count, no model and no id; `max_tokens` bounds output only, so no bound exists for what a request with no answer cost, and it is unmetered. The large-body case of ADR 0036 (2), a `max_tokens` derive could not parse from a body capture kept as a prefix, is now read off every byte of the body (capture/maxtokens) and bounded, so it no longer ends a budgeted run.

Options considered:
- Keep the forwarder's gap-only behaviour: the forwarder, which R38 makes the agent's only route to the model once capture is active, would pass exactly the loss the uprobe path ends a run for. Rejected.
- Report dial failures too (no exemption): fail-closed without exception, but a dial failure is the one case where the leg provably sent nothing (net/http returns the dialer's error before a byte is written), and an agent's SDK retries it as routine; ending a budgeted run at every transient DNS or connect failure would make budgets unusable for no spend. Rejected.
- Charge `max_tokens` plus the request's size as a bound instead of ending the run: input tokens cannot be bounded from bytes without a tokenizer, which is a model-side estimate Tego does not make (ADR 0003). Rejected.

Consequence: A user interrupt before the first response byte (Esc while a coding agent is waiting on the model) ends a run with a token or cost budget; after `message_start` it does not. An upstream that drops connections without answering ends budgeted runs. A run with neither budget is unaffected: its record carries the gap as before. On the uprobe path the same rule now also covers a request dropped because a later response showed it would not be answered, and one the pending table evicted; both were silent. `closePending` counts a request with an unreadable target as `loseConn` does.

*Amended 2026-09-24:* (1) An unanswered request whose path the deriver classifies as spending nothing (derive/anthropic `classifyPath` silent: `/`, anything outside `/v1` such as `/api/...` telemetry, `/v1/messages/count_tokens`, `/v1/models`, the Files API, a batch's status) is not reported, on either path: both ask the deriver (`derive.SilentPaths`, `Dispatcher.Silent`) before reporting. An unknown or ambiguous path (`/V1/messages`, an unreadable target, a tunnel, a host capture never learned) still fails closed, and a lost uprobe connection still counts what it would have carried next, so an h2c upgrade's silent `GET /` does not exempt the h2 after it. (2) An unmetered report that arrives after the agent's main process has exited (awaitExit reaped it) — typically a request tego's own shutdown aborted, the cgroup kill or the forwarder's Close — records `gap what=capture why=unmetered-after-exit` with its count and changes neither the end reason nor the exit code: a budget can no longer be enforced on a run that has ended. Before the exit nothing changes. (3) Under a `cost_usd` budget, a response reporting server-tool requests to a price table that names no `server_tool_per_request` fee at all is unmetered (the watcher reports it through `limits.WithOnUnmetered`), where it was charged $0; `tego compile` warns `[unenforced]` for such a table. Implemented in internal/runtime/capture/forwarder (listener.go silent, markNeverSent), capture/uprobe (events.go unanswered, loseConn), runtime (unmetered.go, run.go quiesced) and limits (price.go UnfeedServerTool, watcher.go).

*Amended 2026-09-24:* point (2) of the note above was too
wide. awaitExit marked the run exited once it reaped the main process, before it waited for the cgroup to empty, so a
descendant that outlived the main process (`sh -c 'agent & exit 0'`) could spend with every unmetered report, the

Note 2026-09-29: the silent classification of that note's point (1), "anything outside `/v1`", is `api.anthropic.com`'s. On another host a `models[]` entry declares for provider `anthropic`, only the root path and `/api/...` paths with no segment inside `/v1` are silent; a gateway's prefixed Messages path (`/anthropic/v1/messages`) is a path the parser does not read, and unanswered it is reported (`derive.HostScoped`).

Note 2026-09-30: a response whose usage carries a billing modifier the price table has no rate for (speed, service_tier, inference_geo other than the plain value, or iterations beyond one message) is unpriced and, under a cost budget, charged at twice MaxCost (usage.modified). Extra iterations bill attempts the counts omit, possibly at another model's rates, and are the residual no charge bounds.

Note 2026-10-03 (superseding the 2026-09-30 residual): a response whose usage carries a rate modifier the price table has no rate for (speed, service_tier or inference_geo other than the plain value) is unpriced and, under a cost budget, charged at twice MaxCost (`usage.modified`). Extra or unreadable `iterations` additionally make accounting incomplete and the exchange unmetered: those attempts may be omitted from the top-level counters, so twice MaxCost cannot bound them. Observed usage and `modified` remain in the record, but a token or cost budget fails closed; a later final output count cannot recover that missing spend. Absent, null, empty or one unambiguous exact-case `type: message` iteration remains metered (`TestExtraIterationsKeepKnownUsageButCannotBoundSpend`, `TestPlainIterationsRemainMetered`; parser version `anthropic-2026-10-3`).

*Amended 2026-11-25:* **A budget that has been crossed closes the forwarder's door before the kill lands.** ADR 0035 and this one say a budget fails closed when it cannot see spend. This note is the other half: spend it has already seen to cross a limit. The limit watcher records the limit line, tells the facade the run's reason is `limit`, and writes `cgroup.kill`, which the kernel delivers later. The forwarder is inline for requests (it reads each one, forwards it and relays the answer; capture only runs beside that), so in that window it kept admitting the agent's next request, and an agent that calls without pausing was answered for as long as the kill took (200 calls in 0.4 s past `repeats: 3` in one run; hundreds of milliseconds on a loaded machine). With a real model each call is slow and the extra spend is usually zero or one call, but a budget's promise should not depend on the model's speed.

1. **A per-run gate, read where a request is admitted.** The watcher keeps the breach that ended the run in one atomic pointer (`limits.Watcher.Closed`), stored once by `trip`, after the limit event is emitted and the facade's reason is set and before the kill is written (the order matters: a refusal that could end the agent first would make the exit read as the agent's own). The runtime hands each capture source that admits requests a function over it (`runtime.LimitGateSetter`, `forwarder.Manager.SetLimitGate`, before Start), and only when the contract bounds `tokens`, `cost_usd`, `repeats`, `wall` or `stall_after`; a run with none wires nothing, and a run with one pays one atomic load per request, no lock and no allocation. The forwarder package learns only `func() (rule, reason, closed)`; it still imports nothing of limits.
2. **A new request is refused at the door, not forwarded.** The check stands at the top of `Listener.ServeHTTP`, after peer admission, so a new HTTP request, a new CONNECT and a new upgrade are all turned away by it (as is the health check, since the run is ending). The gate is asked a second time in `forward()`, at the one place every hold (the body, an ask, a route, a credential) ends and the request is about to go upstream, so a request held when the budget was crossed is refused when it is released, with the same answer and the same line; a hold after that point (the upstream connection being made) is in flight. The refusal line records the path cut to `httppolicy.MaxPathBytes`, as a policy line never carries more (its path is checked first). The answer is the family every other refusal of this listener uses: `403` and a plain-text line (`Tego refused this request: the run reached its limit (limits.repeats) and is being ended; nothing more is sent to the model`), the request body not read on (a body already read is dropped) and the connection closed, and `X-Should-Retry: false`. 403 because the Anthropic and OpenAI SDKs retry only 408, 409, 429 and 5xx, and a 429 or a 503 would be retried by exactly the clients this has to stop; the header is for clients that obey it. It is recorded once per refused request as a `net` line with verdict `refused`, authority `rule`, reason the limit's own code (`limit-tokens`, `limit-cost`, `limit-wall`, `limit-stall`, `limit-repeats`) and rule `limits.<which>`, so the record shows which requests were turned away. Nothing refused reaches the upstream.
3. **What it does not change.** How a limit is counted, the limit line, `run_end reason=limit`, exit 124 and the kill are exactly as before; the gate only refuses. A `ledger_bytes` breach does not close it: it spends nothing, its limit line has no reason code, and a refusal line would only add to a ledger already at its ceiling.
4. **What it does not cover, said plainly.** (a) A request admitted past the second check before the gate closed is in flight and finishes, and is recorded as any other: that is at most the client's own concurrency, plus any exchange the agent made that the pipeline had not yet counted when the limit was crossed (the watcher counts from the record, which trails the agent by the pipeline's backlog: 0 to 4 responses stood after the limit line on a quiet host, and 30 in one run on a loaded host, where the agent did not pause; the gate bounds what the kill's latency adds, not this). (b) A tunnel already open (a `net.proxy` CONNECT or WebSocket) is not cut and carries traffic until the kill: `ProxyPolicy.ValidateLimits` refuses such tunnels only under `tokens`, `cost_usd` and `repeats` budgets, so a run with only `wall` or `stall_after` can have one open (`TestAnOpenTunnelIsNotCutByTheGate` pins it). (c) The uprobe source only reads the agent's own TLS and admits nothing, so it has no door: a run whose contract pins `capture: uprobe` (no forwarder) and any model host the contract lets the agent reach directly keep the window, and a budget there still ends the run at the kill. Closing that would need a refusal in the kernel layers (a live net rule), which is a different mechanism and is not built. (d) A run with capture off counts nothing from model traffic (ADR 0035's `budget-unmetered`), so its token, cost and repeats budgets are not counted and nothing here applies; its `wall` and `stall_after` still end it.

Proved by `TestALimitGateAdmitsWhileOpenAndRefusesOnceClosed` and its siblings (`TestARequestHeldWhenTheGateClosesIsRefusedOnRelease`, `TestARefusalLineClampsAHugePath`) (forwarder: flag clear forwarded, flag set refused locally and recorded once, the stand-in upstream's request count unchanged), `TestTheGateClosesAfterTheLimitLineAndBeforeTheKill` (limits), `TestTheLimitGateIsWiredOnlyWhereABudgetCanCross` (runtime), and on a real kernel by `TestIntegrationALimitStopsTheModelAtTheDoorWhileTheKillLands` (the kill made to land 400 ms late: 4 of 200 calls reached the upstream; without the gate, 200) and the repeats, cost and window integration tests, which hold the same kill late and assert that no request is admitted after the first refusal and that only a handful of responses stand after the limit line (197 to 199 without the gate).


*Amended 2026-11-26 (public issue 99): a budget counts OpenAI-style answers, and the run says why when it cannot count one.* The rule above stays as it is for every answer whose usage cannot be read: **a token or cost budget that cannot count an answer ends the run, never ignores it.** What changes is that fewer answers are in that state, and that the person is told which one it was.

1. **What Tego counts, and by what the contract says.** Usage is read for an exchange by the parser the declared `models[]` provider names (R25), never by what the bytes look like. Provider `anthropic` reads the Messages API (and, on that provider's host, its OpenAI-shaped chat completions, as before). Provider `openai` is new: `internal/runtime/derive/openai` reads **POST /v1/chat/completions** and **POST /v1/responses**, whole or streamed, on whatever host the entry declares (a gateway or a local server speaking those paths is the contract's word that it is OpenAI-style); it claims no host of its own. `provider: openai` was already a valid value, with its base-URL variables; no schema field or enum value is added (spec/agent/v0 `provider` is any non-empty string; VERSIONING.md section 3's add-only rule is not engaged), so a build before this one accepts such a contract and counts nothing of it: the run ends at the first answer (125, run_end detail as above), and `tego rules check` of a build that has the `[budget-uncounted]` warning but not this parser warns for such a contract. `run_start.parsers` of every run now also names `openai` (the field already lists the parsers a build links, `{anthropic, openai, mcp}` in the record spec); no ssl_response of an Anthropic run changes (`TestAnAnthropicRunIsRecordedAsBefore`). The parser does not derive tool-call decisions, so `limits.repeats` does not count OpenAI-style tool calls.
2. **Tego never changes the agent's request.** No stream option is injected. A non-streamed chat completion carries a `usage` object. A streamed one carries usage only if the client asked the API for it (`stream_options.include_usage`); a stream that ends without it is "usage unreadable" exactly as before, with the note `stream without usage`, which `tego run`'s closing lines turn into the client option that makes the API state it, or not streaming, or removing the budget.
3. **Field mapping** (one table, for both shapes; `record.Usage` is Anthropic's four counters, and the budget is input plus output with cache tokens excluded, docs/OPERATIONS.md):

   | OpenAI field | ledger counter | note |
   |---|---|---|
   | chat `usage.prompt_tokens` minus `prompt_tokens_details.cached_tokens`; Responses `usage.input_tokens` minus `input_tokens_details.cached_tokens` | `input` | the cached part is inside the prompt count, so it is taken out, as Anthropic's `input_tokens` leaves its cache reads out |
   | `cached_tokens` | `cache_read` | priced at the table's `cache_read_per_mtok`; not in the token budget |
   | chat `completion_tokens`; Responses `output_tokens` | `output` | reasoning tokens (`completion_tokens_details.reasoning_tokens`, `output_tokens_details.reasoning_tokens`) are a breakdown inside it, billed as output, and are counted once, not added again |
   | `total_tokens`, audio, image, text, prediction and `cache_write_tokens` details | not read | `cache_write_tokens` is part of the prompt count already, so it is in `input` and is priced at the input rate. **Not checked:** whether OpenAI charges more for cache writes; if it does, `cost_usd` could come out low (`tokens` is unaffected). No price is guessed, and the table has no write rate for it |

   A count that is missing, null, negative, not an integer, past the integer range, written twice (also by a JSON escape), or a cached part larger than its prompt, makes the answer unreadable; it is never clamped or taken as zero. Names are read as written (a `USAGE` or `Prompt_Tokens` is not usage), as the Anthropic parser reads its own (R29).
4. **What stays unreadable (fail closed):** an answer cut short (`Truncated`: the client or the agent closed the connection mid-answer, or a capture cap cut it): whatever its prefix holds, because a server that states usage in every chunk would have an early count taken for the answer's, so an interrupted or cancelled stream ends a budgeted run (exit 125) with its own note, "answer cut off"; a 2xx answer with no usage object (a body, or a streamed chat completion whose client did not ask); any other path or method (a POST to the root path `/` is not a health check: only a GET or HEAD of it is silent; embeddings, legacy completions, a stored response's retrieval, a gateway's prefixed path, `/chat/completions` without `/v1`) or method; a stream with a frame that is not an object or does not decode, a second usage chunk, or a changed model or id; a Responses stream with no `response.completed` event (an incomplete or failed response's own events are not read), one without usage, or a second one; a body past 8 MiB (the forwarder's capture cap, which cuts it, the size-cut rule of the forwarder) and, as a bound of its own, past 32 MiB (`openai.MaxBody`) to any caller; a compressed body capture could not decode. There is no wire scanner for OpenAI streams as there is for Anthropic's, so a stream longer than the capture cap is unreadable even when its usage chunk was relayed. A non-2xx answer without usage spent nothing and is not reported.
5. **Cost.** The price table gains no OpenAI entries in `examples/prices.example.yaml` (the prices change, and a table is the user's to keep); a model the table does not name is the unknown-price rule of every model: never $0, charged at the table's dearest rates and recorded `gap why=unpriced-model` (`TestOpenAIAnswersArePricedByTheTable`). The model is the answer's `model`, the request's when the answer names none.
6. **The message.** The run_end detail and exit code (125) are unchanged. `runtime.Result.Uncounted` carries the exchange count and the capture source's account ("POST /v1/chat/completions: usage unreadable", with " (stream without usage)" when the parser said so, `derive.UnreadableWhy`), set only by the call that decided the run's end; `tego run` prints "why:" and "fix:" lines from it. `tego rules check` and the dashboard's check warn `[budget-uncounted]` (a warning at the model entry's line) for a token or cost budget beside a provider outside `agent.CountedAPIs`, a list a test holds equal to the parsers the binary links.
7. **Bounds of the parser** (mirroring the Anthropic parser's): it reads only the kept body, at most `openai.MaxBody`; every member that sets a charge is checked once, in a pass that keeps no copy of the body; a frame with one `data:` line aliases the body, and several lines of one frame are joined with newlines; members that set no charge are skipped by the decoder, not kept (a 4 MiB member beside a small usage reads in `TestHugeAnswers`; allocation was not measured); a panic found by the fuzz targets would be a bug, and the Dispatcher recovers one regardless (R29). Fuzz targets: `FuzzParseChat`, `FuzzParseResponses`, `FuzzClassifyPath`.
