# ADR 0010: fs rules are keyed by the kernel inode object, pinned by an O_PATH fd, via BPF inode storage

Status: accepted 2026-09-21. Supersedes the "(device, inode)" resolution in ADR 0005; the ancestry walk stands.
Superseded in part by ADR 0025 (accepted 2026-09-29, not built for the tier-3 wiring; as of 2026-09-29 built with step A, per ADR 0025's Status; the per-run inode-pointer map held alive by the run's Landlock domain replaces `BPF_MAP_TYPE_INODE_STORAGE`; the `O_PATH` descriptors stay).
Decision: at run start the launcher opens each declared path `O_PATH`, keeps the fd for the run, and assigns the inode a host-wide object id in a `BPF_MAP_TYPE_INODE_STORAGE` map keyed by that fd (`BPF_NOEXIST`, re-read on `EEXIST`); access sets are in a hash map keyed `{cgroup id, object id}`. Hooks call `bpf_inode_storage_get` on each ancestor's inode. Landlock rules are added from the same fds. `compile` never computes an inode.
Why: on btrfs `stat()` reports a per-subvolume anonymous device and inode numbers are unique only per subvolume; overlayfs non-directories can change numbers over their lifetime (verified in `fs/btrfs/inode.c` and the overlayfs docs). Inode storage is keyed by the inode object itself, exactly as Landlock keys its rules by an `O_PATH` fd, and `bpf_inode_storage_get` is available in every LSM hook, unlike `bpf_d_path`.
Consequence: one open `O_PATH` fd per declared entry for the run (raise `RLIMIT_NOFILE`); the inode-storage map is created only after doctor confirms `bpf` in the LSM list, because the `-EOPNOTSUPP` guard for an uninitialized BPF LSM is absent from kernels such as 6.17; overlay layers are not covered by rules on their backing paths (bind mounts are); the walk crosses mounts; tier-3 minimum stays 6.1 (inode storage since 5.10).
