A refusal reaches the agent through up to three channels, strongest guarantees first:

1. **The syscall error, always.** At tier 1 a file or exec refusal is `-EACCES`, whether Landlock makes it (save its `EXDEV` for a rename or link that `REFER` does not allow, spec/policy/SEMANTICS.md §2) or the supervisor does (a `deny_write` modification, docs/p0/supervisor.md R15c; an exec, R16b, where one whose lookup fails as the task's own would keeps that lookup's errno). One exception is below Landlock ABI 3 (kernels before 6.2): Landlock cannot refuse truncation there, so tier 1's seccomp filter refuses `truncate(2)` and an `O_TRUNC` open that is not a write open (`O_RDONLY`, or access mode 3) itself, with `-EPERM` (docs/p0/enforce-landlock.md E31). Tier 2 keeps tier 1's Landlock domain, filter and supervisor, whose refusals stay as above, and adds a fanotify listener whose refusals are `-EPERM`, the bare `FAN_DENY`: no kernel lets that listener send `EACCES` (docs/p0/enforce-cgroup-observe.md §6 E2). Tier 3's exec program refuses with `-EPERM` (spec/policy/SEMANTICS.md §4). The runtime cannot change any kernel's errno, so the reason record, not the errno, says which of them refused. A connect the supervisor refuses, and every other network refusal it makes itself, is `-EACCES` in every tier (docs/p0/supervisor.md R10, SEMANTICS §5, "The errno of a refusal"), as is Landlock's own refusal of a TCP connect or bind (P0 grants no TCP bind, docs/p0/enforce-landlock.md R6). Some other network refusals reach the agent as `-EPERM`, some refused connects among them. At tier 2, the kernel programs refuse with `EPERM` an unconnected datagram the supervisor continues (docs/p0/supervisor.md R13b) and a connect where the kernel's rows and the supervisor disagree (SEMANTICS §5). And from Landlock ABI 6, at tiers 1 and 2, Landlock's abstract-unix scope refuses with `EPERM` a connect or send to an abstract socket bound outside the run's domain (docs/p0/enforce-landlock.md R7), which reaches the agent wherever the supervisor lets that call through to the kernel (`CONTINUE`), as it does under a contract with no `net:` section and for an unconnected datagram (R13b) (docs/p0/supervisor.md, `handleConnect`). A socket the filter's allowlist does not admit under a `net:` section (ADR 0018) is refused by the supervisor with `-EPROTONOSUPPORT` for an inet type or protocol (SCTP, UDP-Lite) and `-EAFNOSUPPORT` for a family (vsock, TIPC, packet), what a kernel without them answers, and recorded (reason `net-not-allowed`); added 2026-09-24. The filter's refusal of an `IPPROTO_MPTCP` socket is `-EPROTONOSUPPORT`, what a kernel without MPTCP answers, so that a runtime falls back to a TCP socket the rules govern; it is not a policy verdict (docs/p0/enforce-landlock.md E30). *Amended 2026-10-05 (ADR 0018 PR 2):* a socket outside that allowlist that reaches creation past the filter (io_uring's `IORING_OP_SOCKET`, or any other path the filter does not see) is refused by a plane mode's `socket_create` with `-EACCES`, any family (docs/p0/enforce-plane.md R14), and at tiers 2 and 3 by `cgroup/sock_create` with `-EPERM`, inet families only, which every run with a `net:` section attaches with its links (ADR 0018 PR 2, attached 2026-10-16; docs/p0/enforce-cgroup-observe.md §5 R4; with a plane mode the plane refuses first, so `-EPERM` is the fanotify fallback's). The latter is recorded with `mechanism: cgroup`; the reason is `net-not-allowed` in all three. *Amended 2026-10-17 (ADR 0018 (7)):* under a `net:` section `setsockopt(SOL_TCP, TCP_ULP)` is refused, whatever the name: by the supervisor with `-ENOENT` on `setsockopt(2)`, what a kernel without that ULP answers, so a runtime that tries kTLS falls back, and at tiers 2 and 3 on any other path (io_uring's `SOCKET_URING_OP_SETSOCKOPT`) by `cgroup/setsockopt` with `-EPERM`, recorded with `mechanism: cgroup`; the reason is `net-not-allowed` in both. *Amended 2026-09-23:* the errnos above are per tier and per mechanism, as stated. *Amended 2026-09-30:* the truncation exception named only an `O_RDONLY|O_TRUNC` open; an `O_TRUNC` open of access mode 3 is the same hole below ABI 3 and is refused the same way.
2. **The reason record, always.** Every refusal is a `refused` event with `reason` (a code from the closed set below) and `rule`. `tego events --last` prints the last refusal; a harness may read `$TEGO_LEDGER/last-refusal.json`, `0600`, which always holds one whole refusal and never goes back to an older one: the latest refusal wins, written at most every 10 ms and once more when the run's ledger closes, so a reader may see it up to 10 ms after the `refused` line (docs/p0/record-ledger.md §3; the write left the ledger's hot path when a refusal flood cut throughput 3.7x, 2026-09-24). *Amended 2026-09-24:* the ledger root is read-denied to the run (agent-contract R6a), so a harness inside the run reads `$TEGO_REASON` instead: the same file, written at the same moments into the run's runtime directory, which the agent can read and not write. `TEGO_REASON` is unset when the run has no runtime directory (a root launcher makes none, and a live root run's directory was never readable to the dropped agent); `$TEGO_LEDGER/last-refusal.json` stays for readers outside the run. *Amended 2026-10-24 ([ADR 0061](../../docs/adr/0061-reason-file-v1.md)):* both copies are the **reason file v1** (`pkg/spec/reason`, schema `spec/reason/v1/reason-file.schema.json`), at most 64 KiB. Its top level is still the latest refusal, every key it had keeping its meaning (`op`, `target`, `reason`, `rule`, `mechanism`, `decision_plane`, `command_rule`, `command_match`), and it adds `v` (1), `run`, `seq` (the refused line's ledger seq), `ts` (RFC 3339 nanoseconds, UTC), `pid`, `text` (one factual sentence, `reason.Text`), `refusals` (the refused lines the run's ledger has written) and `recent` (the newest 32 refusals, oldest first, the latest last, each `{seq, ts, pid, op, target, reason, rule, text}` plus `mechanism`, `command_rule` and `command_match` when set; no other ledger field). Its guarantees: one whole file per read; `seq` and `refusals` only grow, so a newer refusal is never followed by an older one; the 10 ms window and the write at Close and Abandon are as above; the mirror holds the same bytes; `recent` is contiguous, so a reader that keeps the `refusals` it last read as its cursor learns exactly which refusals are new and how many are no longer listed (`File.Since`). A string field past 4096 bytes is cut with its length (`…(N bytes)`), and older refusals leave `recent` while the file would pass 64 KiB, or while refusals with payloads over 32 KiB come faster than the file is written (at most 2 MiB of them wait for it); `recent` stays contiguous and the counts exact, and the ledger line keeps every field whole. *Amended 2026-10-25
([ADR 0077](../../docs/adr/0077-reads-recorded-for-the-reason-channel.md)):* "always" has exceptions, refusals no
Tego component sees and so records: a read the Landlock ruleset refuses under `deny_read` at tier landlock while reads
are neither notified (`reason.reads: on`, `record: full`, an `fs.ask_read` entry, a read gate) nor held (ADR 0069), as
under the default `reason.reads: auto`, the measured off (`run_start.reads_notified` says which); the mount family's
`EPERM` (mount, `pivot_root`, `umount`, remount: Landlock's, enforce-landlock §6); a `bind(2)` at tier landlock with no
`net.listen`, which no notify table holds (enforce-landlock E30); and another LSM's refusal, recorded as `observed`,
`by: other`, never as Tego's (below). A read the filter is told of and Landlock refuses is one `refused` line,
`read-denied`, `mechanism: landlock`, and the reason file's entry carries the mechanism.
3. **The harness hook, when one exists.** *Amended 2026-10-24 ([ADR 0063](../../docs/adr/0063-claude-code-reason-hook.md)), the hook protocol:* this item said Claude Code `PostToolUse` receives `{"tego": {"reason": "...", "rule": "...", "run": "..."}}` and a hook script prints it back; no such payload exists, and Claude Code hooks receive only Claude Code's own payload. The hook is `tego hook claude-code [--reason FILE] [--mode json|stderr]` (`internal/adapters/claudecode`, Layer 3), one command for five events, routed by the payload's `hook_event_name` (at most 1 MiB, one JSON object):

   | Event | `--mode json` (default; the mode the provisioner writes) | `--mode stderr` (a hook wired by hand) |
   |---|---|---|
   | SessionStart | `additionalContext`: `reason.HookInstructions(<reason file>)` (the contract is fixed; a refusal is EACCES or EPERM, a refused command commonly exits 126; the file's path; each refusal is reported once beside the next tool result or at the end of the turn); counts the session | nothing, exit 0 |
   | PostToolUse, PostToolUseFailure | the refusals no hook has shown, as `additionalContext` (`reason.Render`) | the same text on stderr, exit 2 |
   | PostToolBatch | as PostToolUse | nothing, exit 0, nothing claimed (exit 2 would end the agent's loop) |
   | Stop | as PostToolUse, so the turn goes on once; a Stop with `stop_hook_active` (one a Stop hook already continued) prints nothing and claims nothing, new refusals or not, which wait for the next PostToolUse or the next turn's first Stop | text on stderr, exit 2; with `stop_hook_active`, nothing, exit 0 |

   With nothing new an event prints nothing and exits 0. **Exactly once:** the cursor is `hook-state/state.json` beside the reason file (`{v, run, cursor, sessions, deliveries, refusals_delivered}`, at most 4 KiB; `cursor` the highest seq shown, `refusals_delivered` the file's `refusals` at the last claim, `File.Since`'s cursor). Each hook takes `flock(LOCK_EX)` on hook-state/ within 2 s, reads the file and the state, claims, replaces the state by rename, releases the lock and then prints, so of hooks started at once for a parallel batch each refusal is printed by one; a cursor older than the file's `recent` gets every listed refusal and "N more not listed.". A hook killed between its write and its print loses that note; the ledger keeps every refusal. **Discovery:** `--reason`, else `$TEGO_REASON`; neither is a silent exit 0 (outside any run). A path is used only as `last-refusal.json` in `/run/user/<uid>/tego/<run>/` (`reason.DirFor`) or `$XDG_RUNTIME_DIR/tego/<run>/`, or, for `$TEGO_REASON` (the launcher's, runtime-reserved), in `<base>/tego/<run>/` under any absolute base but the root, since `env.pass` may leave XDG_RUNTIME_DIR out of the agent's environment, and so is a `--reason` that is exactly `$TEGO_REASON` (the provisioned settings file's; amended 2026-10-25, ADR 0063 (5)); the file's `run` names the directory. **Fail open:** an argument, payload, reason file, hook-state, lock or state the hook cannot use gives exit 0, nothing on stdout and one line on stderr; json mode never exits 2. Text is at most 4000 characters. The hook's process, from exec to exit, names only its own executable, its own /proc/self entries (`exe`, `uid_map`, `cgroup`, `mountinfo`, `auxv`, `fd/N`; never `root`, `cwd` or a path below `fd/N`), the Go runtime's start-up reads (`/sys/kernel/mm/transparent_hugepage/hpage_pmd_size`, its cgroup's CPU limit: `cpu.max`, or `cpu.cfs_quota_us` and `cpu.cfs_period_us` on cgroup v1), the reason file and hook-state, makes no `bpf(2)` call and starts no process (no machine config, ledger, HOME, network or helper; amended 2026-10-25, ADR 0063 (7)), so it adds no refusal of its own; it is dispatched before tego's command line and not listed in `tego -h`. The launcher makes hook-state/ (ADR 0062) and the settings that install the hook (ADR 0063 (8)); installed by hand in a run without hook-state/ the hook prints nothing. **Delivery** (*amended 2026-10-25, ADR 0063 (8); this said the settings were not merged yet*): a run whose harness is `claude-code` (auto from a command named `claude`, or declared) gets `<runtime dir>/claude-settings.json`, 0444, made by the launcher, listing `<tego executable> hook claude-code --reason <the reason file> --mode json` in exec form (`args` set, `timeout: 10`) for SessionStart, PostToolUse (matcher `*`), PostToolUseFailure (matcher `*`), PostToolBatch and Stop (*amended 2026-10-25*: this gave a bare session `--mode stderr` on three events, the default the measurement was to confirm or flip; Claude Code 2.1.310 runs no hook at all in bare mode, so a bare session is refused, below). A `claude` command's argv becomes `claude --settings <that file> <its arguments>`, the flag at index 1; the command's own `--settings` (inline JSON, or an absolute path read as the launcher may: never under the run's `deny_read`) is taken out and merged into the file, every key and hook of the user's kept and tego's entry appended to each event's array; a path that cannot be read that way, a relative path, `--settings` twice or empty, a value that is not one JSON object, a `hooks` event value that is not an array of matcher groups (objects whose `matcher`, when present, is a string and whose `hooks` is an array of objects with a string `type`), an `env` that is not an object of strings, `disableAllHooks` set to anything but `false`, safe mode (`--safe-mode`, or `CLAUDE_CODE_SAFE_MODE` truthy in the agent's environment or in that `--settings` env block: no hook but a managed policy's loads), bare mode (`--bare`, or `CLAUDE_CODE_SIMPLE` truthy in the same places: no hook runs, "skip hooks", measured in test/e2e/reason-claude/RESULTS.md R2), a `--settings`, `--settings=<value>`, `--safe-mode` or `--bare` after a `--` (*amended 2026-10-25*: Claude Code's option parser takes a `--` as the value of an option that takes one, as in `--model --`, so what follows may still be flags, and tego, which has no table of Claude Code's options, cannot tell such a flag from a prompt), or a file past 2 MiB refuses the run with exit 125 ("pass it inline or set harness: none" for a path; "drop --safe-mode and CLAUDE_CODE_SAFE_MODE, or set harness: none"; "drop --bare and CLAUDE_CODE_SIMPLE, or set harness: none"). The file always sets `disableAllHooks: false` (*amended 2026-10-25*): `--settings` outranks user, project and local settings, so a `true` in `~/.claude`, `CLAUDE_CONFIG_DIR` or the project's `.claude/` (a cloned repository's, or one the agent writes mid-run) cannot turn the hook off; the same `false` lets the user's own hooks there run. For the same reason the file's `env` sets `CLAUDE_CODE_SAFE_MODE` and `CLAUDE_CODE_SIMPLE` to `"0"` (*amended 2026-10-25: `CLAUDE_CODE_SIMPLE` in every run, since there is no bare provision): Claude Code reads a settings file's env block as it reads the shell's, so a lower level's env block could otherwise turn on safe mode or bare mode (no hook in either) in a run whose provision saw neither; whether the real binary takes either variable from a settings env block, and whether the flag level's value outranks a project's there, is not documented, so the pins are kept as a precaution the run below does not show to be needed (*amended 2026-10-25*: this said a lower level's env block cannot turn either on, as ADR 0063 (8) does not). Measured (*amended 2026-10-25; this said the measurement was still to make): with the project's `.claude/settings.json` setting `disableAllHooks: true` and both variables to `"1"`, Claude Code 2.1.310 read that file and still ran tego's hook, which told the refusal (test/e2e/reason-claude/RESULTS.md R8, scenario p); that is the outcome, not which mechanism gives it (the file's `disableAllHooks: false`, its `"0"` values, or Claude Code not taking either variable from a settings env block at all). A managed `disableAllHooks` or `allowManagedHooksOnly` outranks `--settings` and cannot be overridden from it: under such a policy the run says provisioned and the hook does not run (ADR 0063, Consequences). A root launcher makes no runtime directory, so a root run is `reason-unavailable` before any provisioning and its command, its own `--settings` included, runs as given. A wrapper (a command not named `claude`) keeps its argv; the agent's `TEGO_CLAUDE_SETTINGS` names the file in every such run, for a wrapper or the Agent SDK to pass as `--settings "$TEGO_CLAUDE_SETTINGS"`. Nothing is written to `~/.claude`, `CLAUDE_CONFIG_DIR` or a project's `.claude/`. Under an allow-list contract whose rules do not admit the hook, the launcher grants its exact argv (*amended 2026-10-25, ADR 0064*: this said the provision was dropped `hook-not-granted` until a later change granted the hook), and drops the provision `harness-hook-writable` when the agent could rewrite the tego binary or `hook-not-granted` when no exact grant can be made; it is `hook-refused` when the run's rules refuse the hook's argv.

   **Proved by** (*added 2026-10-25*): the real Claude Code 2.1.310, `claude -p` under `tego run` at tier landlock with no network, a dummy key and the model stub behind the forwarder (test/e2e/reason-claude/run.sh, captured in RESULTS.md; local, the binary is needed): the request after a refused Write outside the workspace carries that refusal (the ledger's reason `write-outside-contract`) as the model reads it: the operation and target, the code's sentence ("this run may not write to that path") and the rule, never the code itself, which the hook's text does not hold (*amended 2026-10-25*); after a Bash `git push` refused by `exec.deny`, that refusal (`exec-not-allowed`: "that program is not allowed to run in this run") and its rule; after one turn of two refused `tool_use` blocks, both, and no later request repeats either; after an allowed Write, no tego text; one interactive session (test/poc/interactive-claude/drive.py) the same as the first; `--bare` and `CLAUDE_CODE_SIMPLE` are refused with exit 125 before run_start; and a project `.claude/settings.json` turning hooks off does not reach tego's hook. Claude Code 2.1.310 sends the hook's text after the tool results as a message of role `system`. The CI twin, `TestReasonEndToEndThroughTheStandIn` (test/e2e/reason-claude/fakeclaude, `-tags integration`), runs the first four through the stand-in on every CI run and holds the next request to the golden the real binary wrote (testdata/next-request.golden). A refusal reaches the reason file up to 10 ms after its system call, so a hook that starts sooner tells it with the next note instead (RESULTS.md R7). Not delivered, measured: one value of the command's own `--settings` that Claude Code's schema rejects makes Claude Code drop the whole merged file, tego's hook with it, while run_start says provisioned (RESULTS.md R9).

*Added 2026-09-29 (ADR 0016 step 2):* a refusal of the kernel's LSM chain that no Tego mechanism explains — another LSM's, a third-party fanotify listener's, or one the tier's model does not predict — is recorded as an `observed` action with `by: other` and its `errno` in the payload (spec/record/v1/README.md), never as `refused` with a reason from the set below, which names Tego's refusals only. It gets no `refused` mirror, no `last-refusal.json` and no hook payload: the reason channel never tells the agent that Tego refused what something else refused. Tego's own refusals the tier-2 kernel record carries are recorded under `record: off` too.

Free text never appears in a reason; the rule name carries the specifics. *Amended 2026-10-06 ([ADR 0048](../../docs/adr/0048-exec-command-rules.md) (8)):* exec command rules add no code: a refusal is `exec-not-allowed` with the rule `exec.deny[<entry>]`, `exec.ask[<entry>]` (`completion_unsupported: true`), `exec.args[<tool>]` for a constrained tool's unlisted invocation, `args-unreadable` when the verdict depended on argv past the bound, or `interpreter-unresolved` when a `#!` interpreter's walk failed (answered with that walk's errno), or `image-unreadable` when the image's first bytes could not be read (an execute-only file at tier 1: its `#!` line could name any ruled tool), `loader-unresolved` when a dynamic loader run as a command (`ld-linux-x86-64.so.2 PROG ...`, which runs PROG in-process with no exec of its own) names a program the supervisor cannot read as the loader will (an option no loader it reads has, an operand with no `/`, which glibc searches library paths for, one whose walk fails, or one that is itself a loader), or `loader-program-unmatched` when, in a run whose images are restricted, no `exec.allow` entry grants that program, or `codex-home-exec` when, in a deny-list run, the image or the loader's program lies in the run's own `CODEX_HOME` (added 2026-10-16), or `command-unresolved` when a dispatcher re-dispatches deeper than the matcher resolves (a multicall binary that runs itself, such as busybox's own `busybox` applet, nested past the depth bound), so the exec could still reach a ruled tool and is refused fail-closed. *Amended 2026-10-26 ([ADR 0069](../../docs/adr/0069-held-reads-make-deny-read-true-at-tier-landlock.md)'s note of that date):* a read or an exec the tier-1 ruleset refuses because its `deny_read` enumeration froze at launch (a name made beside an ancestor of an enforced target after the run started) adds no code either: `read-denied` with the rule `deny-read-snapshot`.
